Agent 系统设计：
核心环节与项目自检

围绕一个具体任务，说明系统怎样理解目标、采取行动、使用信息，以及如何判断结果。把这些问题串起来，才能看清一个 Agent 项目的设计是否完整。

一、先说明业务目标

讨论 Agent 之前，先说清楚谁遇到了什么问题、现在如何处理、希望改善什么。否则，工具调用、记忆和多 Agent 都可能只是组件清单，无法解释为什么需要这套系统。

假想示例：为团队做一个内部知识问答助手。用户问“出差怎么报销”，系统需要结合适用地区和最新制度，回答办理步骤并给出出处。这里的目标不是“让模型会聊天”，而是让用户找到适用于自己的可靠信息；缺少地区信息时需要澄清，没有依据时需要说明。

由此可以写下一句项目定义：为谁，在什么输入和约束下，完成什么任务，以什么结果判断完成。再决定检索、工具和执行方式，避免先选框架再寻找需求。

二、五个设计关注点

原文以五个主题组织 Agent 学习。它们适合作为检查系统是否考虑周全的设计维度，不是每次请求都必须依次经过的固定流水线。简单问题可能直接回答，复杂任务才需要规划和多次执行；检索结果也可能促使系统重新澄清目标。

1. 意图识别：到底要完成什么

区分用户说出的句子与实际目标，识别缺失条件、指代和含糊表达。知识问答示例中的“怎么报销”可能需要补充地区和费用类型。关键问题是：哪些信息可以合理推断，哪些信息必须询问，什么时候应该拒绝继续猜测？

2. 计划与执行：如何推进，以及何时停止

把目标转为可执行的步骤，并在得到新结果后决定下一步。工具是执行手段，需要明确输入、输出和权限边界。设计时应考虑工具失败、结果不符合预期、重复操作和停止条件；步骤固定且足够可靠时，也应比较确定流程是否已经能够满足需求。

3. 上下文管理：此刻需要知道什么

决定哪些规则、历史消息、检索内容和工具结果进入当前模型输入，哪些可以摘要或暂不加载。长期保存信息与本轮使用信息是两件事。需要追问：压缩后是否丢失关键条件，过期记忆会不会影响判断，怎样避免无关细节挤占有效信息？

4. 检索：去哪里找依据

外部信息不只有文档，还可能包含业务数据和历史状态。设计应先明确需要什么证据，再选择查找方式。对知识问答而言，找到相关段落还不够，还要判断来源、版本和适用范围；检索不到或来源冲突时，也需要预先定义处理方式。

5. 评估与反馈：怎样知道做得更好

回答流畅不等于任务完成。应围绕业务目标检查结果、依据和执行过程，并把失败样本整理为后续验证材料。用户反馈可以帮助发现问题，但还需要分析失败发生在哪一环，确认修改后是否改善目标能力、是否损害其他表现。

原文提供的是问题框架，并没有在开篇词中展开各环节的实现方案。上面的追问用于引导学习，不能替代具体项目中的设计、测试与取舍。

三、六个项目自检问题

可以用下面的问题检查项目，也可以据此组织面试表达。每个回答都尽量落到可查看的材料上：做过的说明结果，尚未验证的写成假设，计划中的能力说明验证方法。

1. 它解决什么问题，边界在哪里？

说明目标用户、典型任务、输入条件与不支持的情形。准备证据：需求说明、代表性输入、验收条件，以及现有人工流程或已有方案。用这些材料解释为什么值得做。

2. 一次任务实际怎样完成？

沿着一个真实输入，说明目标判断、所用信息、执行动作和最终结果。准备证据：流程图、一条经过必要脱敏的执行记录、工具输入输出与结果出处。只画组件之间的箭头，还不足以证明链路跑通。

3. 为什么选择这套方案？

解释模型、工具、检索和编排方式各自解决的约束，并说明考虑过什么替代方案。准备证据：方案对照、选择理由和已有试验记录；没有比较实验时，把判断依据和待验证项分开写。

4. 哪里会失败，失败后怎么办？

分别考虑理解偏差、信息缺失、工具异常和结果错误，明确重试、澄清、停止或人工接手的条件。准备证据：失败样本、异常处理规则和恢复记录。不能只描述成功路径，也不能把无限重试当作兜底。

5. 如何证明效果，而非只看演示？

将“好用”拆成与目标相关的检查项，例如任务是否完成、答案是否有依据、等待时间和资源消耗。准备证据：测试样本、评分规则、运行条件与实际结果。说明样本覆盖范围，不把一次成功扩展为整体可靠性结论。

6. 下一步改什么，如何确认改进？

从失败记录中选择优先问题，说明预期收益、可能代价及验证办法。准备证据：问题分类、修改记录和同条件下的前后对照。模型、提示词或数据变更后，用保留的样本检查旧能力是否退步。

四、从项目经历中看工程取舍

原文作者提到的项目经历是个人案例，适合用来发现值得追问的约束，不能直接视为通用商业结论或经过验证的架构方案。

  • 生成内容：交付质量与成本。原文作者提到，商家关心可使用的图片或视频，视频生成还受模型成本、效果稳定性和素材质量影响。整理出的设计问题是：最终交付物如何验收，失败后如何返工，人工修订和等待时间是否计入成本？
  • 持续对话：连贯性与信息维护。原文作者提到，用户画像和前后对话一致性是项目关注点。由此可以追问：哪些用户信息值得保存，如何更新与纠正，旧信息如何避免干扰新需求？
  • 数据采集与分析：来源质量与运行稳定性。原文作者提到，数据来源不稳定会限制项目落地。相应的设计问题是：来源变化能否被发现，缺失或过期数据如何标记，采集失败是否会被误当成有效结果？

这些取舍提醒我们，评估 Agent 应覆盖完整交付过程。模型能力只是其中一部分，输入质量、失败处理、人工投入和结果可用性同样需要说明。
