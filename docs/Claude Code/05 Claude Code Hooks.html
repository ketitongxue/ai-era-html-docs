你可能已经在项目规则里写过：“修改文章目录后，检查分类和链接。”但过了几轮对话，AI 还是可能忘记执行。

核心思路

这不一定需要再加一段更强硬的提示词。另一种办法是把检查写成程序，在合适的事件发生后调用它。规则解释要求，检查器判断具体条件，Hook 把检查放进工作过程。

本文用“检查文章目录”说明这个思路。目录格式、代码和测试数据均为原创教学示例，不是网站当前的真实数据接口，也不会自动配置你的 Claude Code。

1. 先区分：提醒、检查和权限

假设一份目录中的每篇文章必须具有标题、分类和地址。我们可以做三件不同的事：

  1. 在项目规则中说明为什么需要分类，让 AI 理解要求。
  2. 用脚本检查字段是否缺失，给出明确的错误位置。
  3. 把脚本接到编辑后的事件，减少依赖临时记忆。

但这三件事都不能证明文章观点正确，也不能代替发布权限。一个检查器完全可能有 Bug，或只检查了部分文件。因此，适合先自动化的是边界清楚、能构造好坏样本的条件，而不是“内容必须精彩”这样的综合判断。

Hook 也不全部是确定性的程序：Claude Code 支持 command 以及模型参与的处理器类型。这里仅使用不调用模型的 command Hook；不要把本例的可重复校验等同于所有 Hooks 的性质。官方 Hooks 参考

4. 实际核验到哪一层？

本稿配套自动测试覆盖：合法目录、空目录、缺字段、空白值、错误类型、重复地址、路径规则、无关事件、目录读取失败及标准输入格式错误。测试通过进程传入模拟事件，检查返回 JSON；不需要消耗模型调用。

但应把三层验证分开看：

层次 验证什么 本稿交付边界
校验函数 好坏数据是否被正确区分 配有可重复执行的测试
命令适配 模拟事件输入能否产生约定输出 配有进程级测试
Claude Code 会话 配置被加载、真实编辑触发、反馈被模型使用 尚未做端到端实测

写教程时，“脚本能运行”和“真实客户端已跑通”必须分开。你可以先在练习目录验证一次错误数据和一次修复，再决定是否接入实际项目。

5. 必须知道的几个缺口

第一，Write|Edit 不会覆盖 Bash 或外部编辑器对同一文件的修改。第二，脚本没有追踪一份写入结果与一次并发修改之间的版本关系。第三，损坏的事件输入、缺少运行环境等属于检查器自身失败，不应被当成“内容通过”。这些都是将教学示例用于实际工程前需要补齐的边界。

发布前仍需独立检查

因此，在构建或发布前还应调用独立检查器，并把非零退出码设为流水线失败条件。不要让一次 Hook 的成功成为唯一发布依据；按项目需要扩展到文件存在性、锚点和外链检查时，也要分别定义超时与失败策略。

最后，检查脚本仍按执行用户的权限运行。不要安装来源不明的脚本，不要让目录正文变成 shell 命令，也不要将密钥写入日志。PostToolUse 的反馈不构成操作系统沙箱或发布授权。

6. 从一个反复出现的错误开始

不必先设计一整套自动化。先选一个你已经遇到几次、又能够明确判定的问题：遗漏分类、重复地址、代码格式不合规。写一个小检查器，用好坏样本证明它确实有用，再接入事件。

比“再也不许出错”更有用的要求，是“这里错了，依据是什么，下一步怎样验证修复”。这也是 Hooks 能融入工程闭环的地方。
