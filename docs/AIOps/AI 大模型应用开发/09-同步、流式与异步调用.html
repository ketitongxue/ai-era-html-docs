09-同步、流式与异步调用

前面几篇我们已经学会了发消息、控制输出、得到结构化结果，但你有没有发现一个问题：只要模型输出稍微长一点，程序就"卡"在那里几秒甚至十几秒，什么都不返回，直到最后一次性全部返回。做离线任务无所谓，可一旦是面向C端用户的产品，这种长时间忙等就是无法接受的。

这一篇我们就来讲模型调用的几种方式：同步、流式、异步。

一、同步调用

我们从第 1 篇开始写的所有代码，其实都是 同步调用（Synchronous Call） 。你发一个 HTTP 请求过去，然后线程就停在那里等，一直等到模型把 全部内容 生成完，服务端一次性把完整结果打包返回，你的代码才继续执行。

# 示意代码，接口以官方文档为准
from openai import OpenAI

client = OpenAI()
resp = client.chat.completions.create(
    model="gpt-5.6",
    messages=[{"role": "user", "content": "用三百字介绍一下杭州"}],
)
# 在拿到完整回复前，这一行会一直阻塞
print(resp.choices[0].message.content)

这段代码简单、可靠、好调试，返回的对象里 usage （token 用量）、 finish_reason （结束原因）一应俱全，写批处理脚本、内部工具、简单任务（响应比较快）时它就是首选。

但它有个绕不开的问题： 对于输出较长的请求，用户要长时间等待 。这里要先回顾模块一讲过的一个关键事实：大模型是 逐 Token 生成 的，它不是一下子想好整段话，而是一个词一个词地逐个生成，前一个 token 是后一个 token 的输入。所以输出越长，生成耗时越久。

假设模型每秒生成 50 个 token，一段 500 token 的回答，光生成就要 10 秒。同步模式下，用户盯着一个转圈的图标看整整 10 秒，屏幕上什么都没有。这 10 秒里内容其实早就一段段生成出来了，只是被服务端攒着暂时没返回。

而且更糟的是： 输出越长，越容易超时 。同步调用是一个从头到尾都不回传数据的长连接，中间一直没有任何数据往回传。可这条链路上多处存在超时限制：你代码里 HTTP 客户端的默认超时、中间的反向代理（如 Nginx）、网关、负载均衡器，很多默认就是 30 秒或 60 秒超时。

一旦模型要生成一篇长文，几十秒才生成完，链路上任何一环等不及先掐断连接，你这边就直接报超时错误，前面已经生成好的内容也全部丢失了。

正因为这个原因，OpenAI、Anthropic、Google 以及国内的 DeepSeek、Qwen 等厂商，在文档里都会明确提醒： 当预期输出较长时，请使用流式调用 ，用持续不断的数据流让连接保持活跃、不被超时断开，从根本上绕开这类超时。这就引出了下一个方案。

二、流式调用

既然内容是一个个 token 依次输出的，我们就不必等全部生成完再返回，而是生成一点就推一点，这就是 流式调用（Streaming） 的核心思想。

技术上，它通常基于 SSE（Server-Sent Events，服务器发送事件） 实现：客户端发起请求后，服务端不关闭连接，而是把生成的内容切成一个个小片段（称为 chunk，数据块），通过同一个长连接持续往回推，直到大模型生成完成，最后发一个结束标记。

你在 ChatGPT 里看到的"打字机"效果，本质就是前端把这些 chunk 一到就立刻渲染出来。

这里要澄清一个新手常犯的误区：流式并不是"前端直连大模型"。真实产品里链路是 分两段 的： 前端（浏览器）通过 SSE 或 WebSocket 跟你自己的应用服务器通信，应用服务器再通过 SSE 跟大模型服务通信 。

为什么这么分？

一是安全，大模型的 API Key 绝不能下发到前端，必须由应用服务器持有并转发；

二是应用服务器在中间还要做鉴权、限流、计费、敏感词过滤、多轮对话拼接等多项业务逻辑。

至于两段为什么用不同协议：应用服务器调大模型是 单向接收 下行 chunk，SSE 这种"服务端单向推流"的轻量协议正好够用；而前端和应用服务器之间往往需要 双向实时 交互（比如用户中途点"停止生成"、发语音、协同编辑），WebSocket 的全双工能力更合适。当然，如果你的场景很简单、只有纯文本单向下发，前端和应用服务器之间直接用 SSE 也完全可以。

在代码里，开启流式后，返回的不再是一个完整对象，而是一个 流 ，你用 for 循环一个个取增量内容：

# 示意代码，接口以官方文档为准
stream = client.chat.completions.create(
    model="gpt-5.6",
    messages=[{"role": "user", "content": "用三百字介绍一下杭州"}],
    stream=True,               # 打开流式开关
    stream_options={"include_usage": True},  # 关键：让最后一个chunk带上usage
)

full_text = ""
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        piece = chunk.choices[0].delta.content   # delta是"增量"，只含新增的那一小段
        full_text += piece
        print(piece, end="", flush=True)         # 到一段就立刻打印

注意这里的字段叫 delta （增量）而不是 message ，每个 chunk 只带 新增的那一小段 ，需要你自己拼接成完整文本。

流式带来的最大价值是 首 Token 延迟（TTFT，Time To First Token） 大幅下降。用户在几百毫秒内就看到第一个字出现在屏幕上，感知上"它在思考、在回答"，等待感会明显减轻。此外还有两个附带好处：内容可 提前展示 （用户读前半段时后半段还在生成），以及可 中断 （用户觉得跑偏了随时点停止，省下后续 token 费用）。

但流式并非没有代价，它把复杂度转移到了 错误处理和结果校验 上，这也是面试和实战里最容易出问题的地方：

  • 流发送到一半失败 ：同步调用要么成功要么失败，但是，流式可能已经推了 200 个字，第 201 个字时连接断了。这时你手里是一段 不完整 的内容，到底算成功还是失败？要不要展示已有部分？重试的话是整个重来还是续传（大多数 API 不支持续传，只能重来）？这些都得业务层自己处理。
  • 结构化输出边接收边解析比较困难 ：上一篇讲的 JSON 结构化输出，在流式下会变成片段，任何时刻拿到的都是 非法 JSON ，没法边接受边解析。常见做法是等接受完所有内容后，再进行解析。
  • usage 统计 ：默认情况下流式响应的中间 chunk 是 不带 token 用量 的，你没法像同步那样直接读 resp.usage ，通常影响不大，最后一个chunk会带上之前所有的token用量累加和。

还有一个环境层面的经典事故必须提醒： 流式在本地运行正常，一部署到线上就"失效"了 。用户还是要等全部生成完才一次性看到。很可能是**网关/反向代理（如 Nginx）的缓冲（buffering）**导致了这个问题：代理默认会把后端返回的数据攒够一批再转发给客户端，正好把你的流式效果缓冲掉了。解决办法是关掉对应路径的缓冲（Nginx 里设置 proxy_buffering off;，或让后端返回 X-Accel-Buffering: no 响应头）。这个坑不知道的话，排查成本会很高。

三、异步调用

流式解决了"让用户少等"的体验问题，但有些场景根本不需要用户实时盯着看，比如：批量给一万条评论打标签、生成一份长报告、夜里跑一批数据。这类任务的诉求变了，不是"快点让我看到"，而是**"别把我的服务器线程占着"**。

这里有一点必须重点强调，否则很容易搞混： 这里说的"异步"，是前端和应用服务器之间的异步，而不是应用服务器跟大模型服务之间的 。也就是说，应用服务器该怎么调大模型还怎么调（同步或流式都行），异步改变的只是"前端不再挂着一条请求死等结果"这件事。前端提交任务后拿到一个任务 ID 就先走了，之后再来查结果。别把它误解成"应用服务器用异步的方式去请求大模型"。

这背后还有一层更关键的服务端考量： 在高并发下，绝不能让长任务长期占用请求处理线程（Web 线程） 。

要知道，Web 服务器（如 Tomcat、Jetty）用来接请求的线程池是很宝贵且有限的，可能就几百个。如果每来一个长任务就占着一个 Web 线程死等几分钟，那么稍微来一点并发，这几百个线程立刻被占满，后续请求连"被接收"的机会都没有，整个服务直接瘫痪、无法响应。

当单个任务耗时极长（几分钟甚至更久），你不可能让一个 HTTP 请求挂在那里等，用户的浏览器早超时了。正确的做法是：Web 线程只负责"接收请求、把任务塞进队列、立刻返回任务 ID"这种毫秒级的工作，随即被释放去处理下一个请求；真正耗时的大模型调用则丢进 任务队列 ，交给 独立的后台线程池 慢慢处理，两者互不抢占。客户端再通过 轮询（Polling） 查任务状态，获取处理结果。

有些大模型厂商甚至直接提供了 Batch（批处理）接口，你把一大批任务打包提交，它异步处理完再给你结果，价格还更便宜。

以 OpenAI 为例。你不是在一个 HTTP 请求里直接塞多个任务，而是先在本地准备一个文本文件：每一行写一条完整的 JSON，对应一次普通的模型调用。这种「一行一条 JSON」的格式叫 JSONL（JSON Lines） 。

文件准备好后，先把它上传到厂商的文件接口。上传成功会返回一个文件对象，里面最重要的是 id ，类似 file-abc123 。接着拿着这个 id ，作为 input_file_id 去提交一个批次，等于告诉厂商：「去跑我刚传上去的那份文件」。提交接口立刻返回 batch_id ，之后轮询这个 ID 的状态、下载结果即可，不用自己维持一条长时间的 HTTP 连接。Qwen 等国产厂商也有同类接口，路径和字段以各自文档为准。

下面这个 batch.jsonl 只有两行，分别给两条评论打情感标签：

{"custom_id": "cmt-1", "method": "POST", "url": "/v1/chat/completions", "body": {"model": "gpt-5.6", "messages": [{"role": "user", "content": "判断情感：物流很快，包装也严实。"}]}}
{"custom_id": "cmt-2", "method": "POST", "url": "/v1/chat/completions", "body": {"model": "gpt-5.6", "messages": [{"role": "user", "content": "判断情感：等了一周才发货，客服也不回。"}]}}

# 示意，接口以官方文档为准

# 1. 上传 JSONL，purpose 必须是 batch
#    返回里带 "id": "file-abc123"，下一步原样填进去
curl https://api.openai.com/v1/files \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -F purpose="batch" \
  -F file="@batch.jsonl"

# 2. 把上一步的文件 id 填进 input_file_id，提交批次
#    返回里带 "id": "batch_abc123"
curl https://api.openai.com/v1/batches \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "input_file_id": "file-abc123",
    "endpoint": "/v1/chat/completions",
    "completion_window": "24h"
  }'

# 3. 用上一步的 batch_id 轮询状态；completed 后再用 output_file_id 下载结果文件
curl https://api.openai.com/v1/batches/batch_abc123 \
  -H "Authorization: Bearer $OPENAI_API_KEY"
