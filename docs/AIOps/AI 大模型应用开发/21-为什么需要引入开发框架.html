21-为什么需要引入开发框架

前面四个模块，我们讲了大模型应用开发的最基本的组件：怎么调模型、怎么写提示词、怎么输出结构化数据、怎么搭建 RAG。

在前面的文章中，我们多次提到：这些事情，框架大多已经帮你做好了。在真实的项目开发中，大多数情况下，我们都会使用开发框架简化开发。

因此，这个模块，我们就来讲解大模型应用开发常用的两个框架Spring AI（Java语言）和LangChain（Python语言，对应的Java语言版本是LangChain4J）。

第一篇文章，我们先把一个根本的问题讲清楚： 框架到底替你解决了什么，它为什么值得你额外学习一套 API。

一、框架的作用之一：复用

假设你要做一个常见的企业知识问答服务：用户提问，从公司文档库里检索资料，交给模型作答，答案要带引用，要能流式输出（打字效果）。

这个需求你现在完全有能力实现，前四个模块讲的内容已经够用了。

我们来看一下，如果不使用开发框架，从零手写，需要写哪些代码：

  • 接入模型：读官方 SDK 文档，处理鉴权、超时、重试。
  • 历史消息：自己维护一个 messages 数组，实现多轮对话。
  • 提示词模板：写个字符串替换，把检索到的资料填进模板。
  • 解析输出：拿到大模型输出，反序列化为对象，失败了带着报错重试。
  • 处理文档：找 PDF 解析库、写切分逻辑、抽取出元数据。
  • 生成向量：调 Embedding 接口，给切块生成向量。
  • 访问向量数据库：读向量数据库的API文档，学它的建表、写入和查询 API。
  • 检索并组装上下文：混合检索、查询重写、重排序、拼模板等。
  • 流式返回：处理 SSE 分块，把增量文本推送给前端。
  • 日志记录：统计每次大模型调用的 Token 和延迟等。

我们发现，以上大部分任务，都跟业务无关，你的业务是企业知识问答，但大部分时间都花在了「怎么把 PDF 变成文本」「怎么把一个向量写进数据库」这类技术细节上。

更麻烦的是，每一处你都得自己做决定：切块多大、重叠多少个字、向量字段建什么索引、超时设几秒、重试几次、退避算法怎么设计。这些决定和业务无关，但每一个都要查资料、做试验。做完之后，它们分散在项目的不同模块中，半年后只有你自己知道当初为什么那么写。

而这些非业务代码，几乎每一个大模型应用都要重写一遍。既然大家写出来的实现都差不多，就没必要各自重复一次。 这就是框架存在的第一层意义：复用。

需要说明的是，框架复用给你的不只可直接使用的现成代码，还有另外两点。

一是一整套比较合理的默认值。 向量字段建什么索引、用哪种距离函数、超时设多少、重试几次、退避怎么设计，框架都给了默认配置。这些默认值不一定最优，但它让你能先把功能跑起来，等真的遇到瓶颈再去调整。

二是现成的生态集成。 这一条容易被低估。你要接一个新的向量库、读一种不常见的文件格式、对接一个国产模型平台，开发框架的社区里大概率已经有现成的集成包，安装后即可使用。如果自己从零对接，光阅读文档就要花费半天。

二、框架的作用之二：抽象

不过复用只解决了「少写代码」这一个问题。还有另一个问题，它解决不了。

产品说，我们要试试国产模型，对比一下效果和成本。你打开代码一看，OpenAI 响应和 Anthropic 响应的字段完全对不上，流式分块的结构也不一样。

运维说，内存向量库不能上生产，换成 pgvector。你发现RAG检索那部分代码从建表到查询整个要重写。

虽然功能能跑起来，但任何一处变化都要大范围改造代码。 个时候，框架的第二个作用就体现出来了，也就是：抽象（或封装）。

框架的做法是： 把每一类工作都抽象成一个接口，业务代码只面向接口编程，至于底层用的是哪家实现、依赖了哪个 SDK，全都被挡在接口后面。

以「把消息发给模型，拿回回复」这件事为例，Spring AI 把它抽象成 ChatModel 接口，LangChain 抽象成 BaseChatModel 。你的业务代码只调用这个接口的方法，代码里既不会出现 OpenAI SDK 的类名，也不会出现某一家厂商特有的响应字段。接口之下，框架自己提供了一批开箱可用的实现，比如：

  • ChatModel ：Spring AI 官方带了 OpenAI、Anthropic、Gemini、Bedrock、Ollama、Mistral、DeepSeek 等大模型调用实现；LangChain 对应的是 langchain-openai 、 langchain-anthropic 、 langchain-google-genai 、 langchain-deepseek 这些独立发版的包。
  • VectorStore ：两边都覆盖了内存实现、pgvector、Redis、Elasticsearch、Milvus、Qdrant 这些常见选择。
  • 读文件的 DocumentReader / DocumentLoader ：PDF、Word、Markdown、HTML、CSV 都有现成的实现。

更关键的一点是，这批实现并不需要全部由框架官方来写。 接口是公开的，任何人都可以自己实现一份，再作为独立的依赖集成进来。

举两个实际的例子。通义千问的接入，Spring AI 官方并没有做，而是由阿里巴巴维护的 Spring AI Alibaba 项目提供 ChatModel 实现；LangChain 这边， langchain-milvus 、 langchain-qdrant 这类包是由向量库厂商自己维护的。

所谓 Spring AI、LangChain这些框架，核心就是「一批抽象接口」加「一批默认实现」。

功能 Spring AI 接口 LangChain 接口

从上表中，我们可以发现，左右两列几乎可以逐行对上。这也意味着： 你只要真正掌握其中一个开发框架，另一个对你来说就只是换了一批名字。 所以这门课不打算把两套框架的 API 逐个讲一遍，而是讲清楚这些抽象本身。

有了这层认识，再回头看没有框架时的依赖关系，差别就很直观了：

接口这一层，换来的最直接的收益就是可替换性。

开发阶段用内存向量库，速度快，也不用额外部署中间件；上线换成 pgvector，业务代码一行不用改，只需要改依赖和配置：

# LangChain：换向量库只影响构造那一行，下游用法完全不变
# store = InMemoryVectorStore(embeddings)
store = PGVector(embeddings=embeddings, connection=DSN, collection_name="docs")

retriever = store.as_retriever(search_kwargs={"k": 5})

# Spring AI：换向量库 = 换一个 starter 依赖 + 改配置，注入点仍然是 VectorStore
spring:
  ai:
    vectorstore:
      pgvector:
        index-type: HNSW
        distance-type: COSINE_DISTANCE

三、框架的作用之三：编排

有了接口，也有了实现，还差最后一步：把这些组件按顺序连起来，构成一次完整的调用。这一层就是编排。

编排也是两个框架风格差异最大的地方。

Spring AI 通过给 ChatClient 加 Advisor 实现编排。

ChatClient 是一个流式 API，通过链式调用把一次请求描述清楚。Advisor 则是拦截器：每一次调用都会顺着一条有序的 Advisor 链走一遍，每个 Advisor 都可以在请求发出之前修改请求、在响应返回之后修改响应。检索增强、对话记忆、日志，在 Spring AI 里全都可以做成 Advisor。

这种方式 Java 开发者应该不陌生，它和 Servlet Filter、Spring Interceptor、AOP 是类似的设计思路。

String answer = chatClient.prompt()
        .user("出差住酒店最多能报多少钱？")
        .advisors(new QuestionAnswerAdvisor(vectorStore))  // 插入一个检索增强
        .call()
        .content();

LangChain 给的是 Runnable 加一个管道操作符。

LangChain 把每个组件都实现成 Runnable ，也就是一个统一的可调用对象，都有 invoke 、 stream 、 batch 这几个方法。然后用 | 把它们接成一条链，前一个的输出就是后一个的输入。这套写法叫 LCEL（LangChain Expression Language） 。

chain = prompt | model | parser
answer = chain.invoke({"question": "出差住酒店最多能报多少钱？"})

这是典型的函数式管道思路，和 Unix 的管道、Java Stream 的设计思想类似。

关于 LCEL 有一个流传很广的误解，这里澄清一下： LCEL 没有被废弃。 Runnable 至今没有任何废弃标记， prompt | model | parser 这种线性组合依然是最合适的写法。变的是官方的重心整体转移到了 create_agent 和 LangGraph 上（讲Agent开发的时候再讲）。

所以，判断标准其实很清楚：链路是线性的就用 LCEL；一旦出现分支、循环、跨步骤重试、状态持久化、人工介入，就该换成 LangGraph。 在Agent开发这个大背景下，LCEL 是被淡化，不是被淘汰。

两种编排方式没有优劣，但反映了两边不同的设计思路： Spring AI 是「一次调用，中间插入一组拦截器」，LangChain 是「一组小函数，串成一条链」。 后面几篇的对照代码里，你会反复看到这个差别。

当然，你也完全可以摒弃框架提供的自动编排功能（Advisor、ICEL），自己去写代码编排业务流程，也是没有任何问题的，也是很常见的写法。

四、框架技术选型

复用、抽象、编排讲完了，接下来是一个很实际的问题：具体该选哪个框架。

这里要一起讨论的共有三个框架：Python 这边的 LangChain，Java 这边的 Spring AI 和 LangChain4j。

LangChain：社区驱动，功能最完备，入门成本也最高。

它诞生于 2022 年 10 月，比 ChatGPT 还早一个月，是这个领域最早的框架。它靠社区驱动发展壮大，各种模型、向量库、工具的集成非常完善，覆盖了大模型应用开发的各类能力。

社区驱动的另一面是不停地往里塞东西，导致框架过于复杂庞大。2025 年 10 月的 1.0 版本对此做了修正：主包只保留构建 Agent 所需的核心组件，其他各种集成拆成了包单独发版，结构因此清晰了很多。

Spring AI：官方出品，追求与 Spring 深度融合。

它是 Spring 团队的官方项目，1.0 GA 在 2025 年 5 月发布，2.0 GA 在 2026 年 6 月发布。对一个已经在跑 Spring Boot 的团队来说，接入成本非常低。

LangChain4j：Java 生态里不依赖 Spring 的另一个选择。

它启动于 2023 年初，1.0 GA 和 Spring AI 同在 2025 年 5 月。名字虽然来自 LangChain，但它不是 LangChain 的官方移植，两个项目的代码和演进路线完全独立，只是在功能划分上互相借鉴。

LangChain4j 是一个不依赖任何容器的纯 Java 库，所以，当项目没有用 Spring Boot 时，它基本上是 Java 这边唯一的现成选择。不过，它也提供了集成到 Spring Boot的官方 starter。

那到底该怎么选？

第一，你的业务系统在哪个生态。 这一条权重最大，基本是决定性的。大模型能力最终要接进订单、工单、客服、报销这些既有系统里。如果这些系统是 Spring Boot 写的，为了用 LangChain 而单独再开一个 Python 服务，就要额外承担一次跨进程调用、一套部署运维。这个代价通常比框架之间的差距大得多。

第二，你的需求离前沿有多近。 如果做的是标准的 RAG 问答、文档摘要、工单分类等业务，三个框架都够用，按第一条选就可以。但如果要做复杂 Agent、多 Agent 协作，或者需要及时跟进业界刚出现的新方法，LangChain是更好的选择，因为新方法基本都先在 LangChain 落地。

现实中最常见的落地形态其实是混合： 在线服务用 Java，离线链路用 Python。 用户请求走 Spring Boot，检索、模型调用、结果拼装都在 Java 里完成；文档解析、切分、批量向量化、效果评测等这些离线任务放在 Python里完成。两边通过向量库和数据库交换数据，各用各的强项。
