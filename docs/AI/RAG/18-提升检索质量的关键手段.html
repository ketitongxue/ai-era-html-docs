18-提升检索质量的关键手段

前面讲到，RAG 有六个关键步骤：解析、切分、向量化、向量存储、检索、上下文组装。

前4个属于索引阶段，已经都讲完了，这节课我们来讲检索。

有人会认为，检索不就是拿用户问题在向量数据库中查询Top-K（比如Top5）个语义最接近的文本片段吗？这有什么好讲的？

看了这篇文章，你就知道，参照基本原理，只能产出demo，要想做成产品级功能，要解决的问题还有很多。

一、一个问题是怎么被检索到的

假设知识库里已经存好了公司那份《差旅报销制度》，切成了若干片段，每个片段都算好向量存进了向量库。现在用户问了一句：

出差住酒店最多能报多少钱？

从收到这句话到拿回资料，中间要走五步。

第一步，把问题也变成向量。 库里存的是向量，用户的问题是文字，两者无法直接比较。所以先使用 Embedding 模型把这句话编码成一个向量。

这里有一条硬性约束，上一篇强调过： 建库用的是哪个 Embedding 模型，查询就必须用同一个。 你建库时用 text-embedding-3-small ，查询也必须用它，否则两边的向量根本不在一个坐标系里，算出来的相似度毫无意义。

第二步，在向量数据库里做近似最近邻检索。 这个不需要我们自己去实现，向量数据库已经封装好了，调用接口即可。

第三步，向量数据库返回 Top-K 个片段。 比如取最相似的 5 条，连带它们的相似度分数和元数据一起返回。

第四步，把这几条片段拼进提示词。 填入一段「请根据以下资料回答问题」的Prompt模板里，和用户的问题一起交给大模型。

第五步，模型依据资料作答。 只要那几条片段里确实包含答案，模型就可以据此给出回答。

这条链路很直观，把它跑通并不难。但要让它在真实问题上答得准，每一步都有具体问题。我们就从链路的第一步开始，一步一步看它会在哪里出问题。

二、查询重写

链路的第一步是「把用户问题编码成向量」。但你有没有想过： 用户那句原始提问，本身就适合用来检索吗？

答案是，很多时候并不适合：

  • 多轮对话里指代不明。 上一轮问「差旅住宿标准是多少」，这一轮问「那交通费呢」。用「那交通费呢」去检索，必然检索不出想要的片段。
  • 太口语、掺杂无关信息。 「我下周要去上海出差三天，公司这边住酒店那个报销的标准大概是多少啊」，一批噪声词会使查询向量偏离目标语义。
  • 术语和文档对不上。 用户说「加班费」，制度里写「延时工作补贴」。
  • 一句话包含多个意图。 「住宿和交通标准分别是多少」，一次检索很难同时命中两类片段。

解决的办法也很直接： 先把问题改写好，再用来检索。 这就是 查询改写（Query Rewriting） 。我们分情况来看。

1. 多轮对话查询重写

多轮对话的查询重写，这不是可选优化，而是 只要你的 RAG 支持多轮对话就必须做的 。做法是用一次便宜的模型调用，把当前问题补成一个独立可检索的句子：

REWRITE_PROMPT = """请把用户的最新问题改写成一个不依赖对话历史、可独立检索的完整问句。
只补全指代和省略的信息，不要扩展、不要回答问题。若原问题已经完整，原样输出。

对话历史：
{history}

最新问题：{question}
改写结果："""

def rewrite(history: str, question: str) -> str:
    resp = client.chat.completions.create(
        model="gpt-5.6-luna",       # 这类小任务用便宜快的档位即可
        messages=[{"role": "user", "content":
                   REWRITE_PROMPT.format(history=history, question=question)}],
    )
    return resp.choices[0].message.content.strip()

# "那交通费呢" → "公司差旅报销制度中的交通费标准是多少"

2. 多查询检索

用一次便宜的模型调用，把一个问题改写成 3 个不同角度的问法，并行检索，再把结果合起来（怎么合，下一节讲）。

它提升召回率的效果较好，本质是用多个查询覆盖同一语义的不同表达，弥补单个向量的偏差。代价是检索次数翻倍，外加一次模型调用。

3. 问题拆解

还有一类问题，无论怎么改写单个查询都命中不了，叫 多跳问题 ：「负责 A 项目的人，他所在部门的年假政策是什么？」

难点在于，一次检索只能带回跟原始问句相似的片段，而这个问题的答案需要连着查三次，中间那两跳的信息根本没被检索到。

做法是利用大模型将问题拆成子问题，然后再用子问题串行检索：先查「A 项目负责人是谁」，拿到「张三」，再查「张三所在部门」，最后查「该部门年假政策」。这已经很接近 Agent 的做法了。我们在后续讲解Agent开发的时候再讲。

4. HyDE

一个反直觉但有效的技巧。

HyDE（Hypothetical Document Embeddings，假设文档嵌入） 的做法是：先让模型凭自己的知识 生成一个假设答案 ，再用这个假设答案去检索。

为什么假设答案仍然有效？因为向量检索本质是「用文本与文本比较」，而 问句和陈述句的文体差异本身就在拉低相似度 。假设答案哪怕事实是错的，它的文体、术语、句式都和真文档相似，反而更容易检索出相关的资料。

三、混合检索

问题改写好了，进入链路第二步：向量检索。

向量检索擅长「语义相近」，但它对精确的字符串很不敏感。 比如：

  • 产品型号 SKU-8842-B 、错误码 E1043 、订单号、版本号
  • 人名、缩写、内部项目代号（ 有面项目 、 OKR-Q3-07 ）
  • 罕见的专有名词，尤其是训练语料里很少出现的内部术语

用户搜「E1043 是什么错误」，向量检索会返回一批「关于错误处理的通用说明」，因为在语义空间里， E1043 和 E1044 几乎是同一个方向。 它理解的是「这是个错误码」这个概念，而不是「就是这一个码」。

数字和否定也有类似的问题：「不含糖的饮料」和「含糖的饮料」向量非常接近，一个「不」字翻转了意思，但在语义向量里只是个微小扰动。

怎么解决这个问题呢？

换一种完全不同的检索方式来配合。 关键词检索（最经典、最主流的算法是BM25，Best Matching 25） 做的是另一件事：统计词的出现频率和稀有度。 E1043 这种词在全库里极其罕见，一旦命中，BM25 会给它极高的权重，直接把那一条放到第一名。

因此，向量检索和关键词检索正好互补：

向量检索 关键词检索（BM25）
同义、换句话问 强 弱
精确型号 / 编号 / 缩写 弱 强
罕见专有名词 弱 强
长句、口语化提问 强 弱

于是，最自然的做法就是 两路都跑，再把结果合起来 ，这就是 混合检索（Hybrid Search） 。

用 RRF 融合两路结果

两路检索结果在合起来时，会碰到一个麻烦：BM25 的分数可能是 0 到 30 多，余弦相似度是 0 到 1，尺度完全不同，没办法合并排序。

工程上最常用的解法是 RRF（Reciprocal Rank Fusion，倒数排名融合） 。它的思路很简单： 不看分数，只看排名。

它的处理逻辑分三步：

  1. 按排名给分。 每一路检索结果都是一个按相关性从高到低排好的片段列表。对某一路里排在第 rank 位的片段，给它记一个分数 1 / (k + rank) 。排名越靠前分数越高，分数从第 1 名往后衰减得很快。头部几名拉开明显差距，尾部则趋于平缓。这里的 k 是个平滑常数，通常取 60，用来压低第 1 名的绝对优势、让后面的名次也能有所贡献。
  2. 跨路累加。 把同一个片段在各路里拿到的分数相加。于是一个片段只要在多路里都排得靠前，分数就会叠加、排到最前；只在单路命中的片段则相对靠后。
  3. 重新排序取头部。 按累加后的总分从高到低排序，取前若干条作为融合结果。

举个例子，设 k = 60 ，两路各返回 3 条：

  • 向量检索： c17 （第 1）> c23 （第 2）> c88 （第 3）
  • BM25： c05 （第 1）> c17 （第 2）> c23 （第 3）

按 1 / (k + rank) 给分再跨路累加：

片段 向量检索得分 BM25 得分 累加总分
c17 1/61 ≈ 0.0164 1/62 ≈ 0.0161 0.0325
c23 1/62 ≈ 0.0161 1/63 ≈ 0.0159 0.0320
c05 — 1/61 ≈ 0.0164 0.0164
c88 1/63 ≈ 0.0159 — 0.0159

最终排序是 c17 > c23 > c05 > c88 。注意 c05 明明是 BM25 的第 1 名，却掉到了第 3，因为它只在一路里出现；而 c23 虽然两路都只是第 2、第 3 名，靠着双路累加反超了它。这正是 RRF 想要的效果： 在多路里都被认可的片段，比只在单路排第一的片段更可信。

RRF 的好处是 不需要调权重、不需要归一化，天然免疫尺度差异 。而且在两路里都排得靠前的片段会自动累加分数、排到最前，这个性质很符合直觉。上一节的多查询检索，合并结果用的就是它。

在实际的项目中，具体如何实现混合检索呢？

Elasticsearch 原生支持 BM25 + 向量 + RRF，pgvector 可以配合 PostgreSQL 的全文检索来实现混合检索，Milvus、Qdrant 也都提供了混合检索接口。 优先用一个库同时支持两路检索，否则，自己维护两套存储很容易数据不一致 ：向量库删了、关键词索引没删，于是检索到了已删除的内容。

需要注意的是，中文 BM25 必须先分词。BM25 是按「词」统计的，英文天然用空格分词，中文却是一串连续的字，得先切成词才能统计。切词这件事不用自己造轮子，用现成的分词器即可，具体用哪个取决于你的技术栈：

如果混合检索用 Elasticsearch，就给它装上 IK 分词插件、在字段上配好即可；

用 PostgreSQL 全文检索，得额外装中文分词插件（ zhparser 或 pg_jieba ），否则它默认按空格切，中文会整句当成一个词；

Milvus、Qdrant 这类向量库做 BM25，要在建索引时指定中文分词器（Milvus 内置了 jieba analyzer，Qdrant 则需自己接入分词）。

另外无论用哪种，都要把内部术语、产品型号加进自定义词典，否则「有面项目」会被切成「有」「面」「项目」三个词，检索时就对不上了，无法命中。

四、重排序

进入链路第三步：向量库返回 Top-K。先想清楚一个问题： K 到底取多少？

新手常见做法是检索 Top-3 直接交给模型。这个 K 通常偏小，正确片段常常无法进入候选集。正确的思路是 分两个阶段 ：召回阶段把候选放宽，生成阶段再收紧。收紧不一定每次都取满固定条数，也可以按分数阈值来，下面会讲。

召回阶段的 K 放大，代价很低（向量检索本身很快），换来的是召回率明显提升。真正贵的是放入提示词的那部分，所以最终交给模型的条数才需要收紧。3 ~ 5 是常见的 上限 ：500 字的 chunk 取 5 条大约 2500 字。 再往上加的话，收益会迅速衰减，甚至变成负的 。无关内容变多，Lost in the Middle 的影响就变严重了。

但召回阶段放宽到几十条之后，问题就来了： 怎么从候选的几十条里挑出该进提示词的那几条？向量数据库的排序可靠吗？

先给你答案：向量数据库的不够可靠。向量检索给出的排序偏粗，第一名未必真是最相关的那条。

为什么呢？

因为，向量检索是「双塔（Bi-Encoder）」结构：

关键在于： query 和 doc 是分别编码的（即Embedding），两者在编码过程中彼此独立。 doc 的向量在索引阶段就算好了，跟将来会来什么查询毫无关系。

一段几百字的文档被压成一个固定向量时，模型根本不知道用户将来要问什么，只能把所有信息平均地压进去。 那些对当前问题至关重要的细节，很可能在压缩中被抹平了。

想排序排得准，就必须对 query 和 doc 联合编码。 交叉编码器（Cross-Encoder）正是用来做这件事的： 通过向量检索得到的30~50条doc片段，跟query拼在一起，通过交叉编码器进行再次排序，这一步就叫做 重排序（Rerank） 。

query 和 doc 拼在一起送进模型，每一层注意力都能让问题里的词和文档里的词直接交互。比如问题里带了「一线城市」这个限定条件（起缩小范围作用的修饰词），模型能判断出「doc 中的第三句正好回答了一线城市这个档位下的报销标准」这种细粒度的对应关系，而这正是只看整句向量的双塔容易忽略的。

选型上，中文可用的重排模型不少，而且不少是国产的：

  • 要私有化部署 ：智源（BAAI）的 bge-reranker-v2-m3 、网易有道的 bce-reranker-base_v1 ，都是开源、中英双语、一张普通显卡就能跑。
  • 不想自己部署、直接调 API ：阿里通义的 gte-rerank-v2 （阿里云百炼）、硅基流动托管的 bge-reranker-v2-m3 等；国外的有 Cohere Rerank、Jina Rerank。
  • 复用通用大模型 ：也可以直接让 gpt-5.6-luna 、 deepseek-v4-flash 这类便宜模型给候选打分，灵活但慢且贵，不适合高并发。

调用起来并不复杂，以阿里通义 gte-rerank-v2 为例（通过阿里百炼）：

import dashscope
from http import HTTPStatus

resp = dashscope.TextReRank.call(
    api_key="sk-xxx",                 # 阿里百炼的 API Key
    model="gte-rerank-v2",
    query="出差住酒店最多能报多少钱？",
    documents=[
        "一线城市住宿每晚上限 800 元，二线 500 元。",
        "交通费：高铁二等座凭票实报实销。",
        "出差每天发放伙食补贴 100 元。",
    ],
    top_n=20,                         # 先把候选的分数都算回来，截断留给自己做
    return_documents=True,
)

if resp.status_code == HTTPStatus.OK:
    for r in resp.output.results:
        # r.index 原始下标，r.relevance_score 相关性分，r.document.text 原文
        print(r.relevance_score, r.document.text)

重排序做完，每条候选都有一个更可靠的相关性分数。这时候要决定： 哪些片段真正塞进提示词？

固定取前 3~5 条这种方法能用，但不够好。

  • 真正相关的只有 1 条，你却硬塞 5 条，后 4 条是噪声。
  • 问题本身要对照好几段制度（「住宿和交通标准分别是多少」），相关片段有 7 条，你却在第 5 条砍断，答案缺一块。

其实，最终这一刀，也可以 按分数阈值切 ：只留重排序分数达到阈值的片段，条数随问题浮动。

反过来，如果 7 条都在 0.80 以上，阈值会把它们都留下，不会被「最多 5 条」提前砍掉。当然也不能无限装，工程上更稳妥的是 两道闸一起用 ，而不是二选一：

  1. 先按阈值过滤。 低于某个阈值的直接丢掉。这一步解决「不相关的不要硬塞」。
  2. 再按上限截。 剩下的按分数从高到低，截到 Token 预算允许的最大条数（常见还是 3~5 条）。这一步解决「相关的太多也装不下」的问题。

如果阈值过滤完之后，候选的资料为空了，该怎么办？正确的做法是走「未找到相关资料」这条路径，提示词里写死「资料不足就说不知道」。

阈值该设置为多大？

一个靠谱的做法是，准备二三十个真实问题，人工标一下「这条该不该进提示词」，画出重排序分数的分布：该进的落在哪个区间，不该进的落在哪个区间，把阈值放在两堆之间。

五、上下文扩展

经过重排序之后，排序也准了，最相关的片段已经排在前面。可有时候你会发现：命中的片段确实相关，但它信息不全，模型还是答不好。

原因在第 2 篇讲过的那个矛盾：

chunk 越小，检索越准但上下文越不完整；chunk 越大，上下文越完整但检索越不准。

先说为什么大 chunk 检索不准。 一个片段只有一个向量， 一段里同时讲了五个话题，这个向量就是五个方向的平均值，跟其中任何一个具体问题都不够接近。用户问的是第三个话题，向量被另外四个话题拉离了目标方向。也就是说，向量的信息被稀释了。这也解释了一个反直觉的现象：明明把 chunk 调大、让片段包含了更多信息，检索效果反而变差。

那反过来，切得足够小就没问题了吗？同样不行。检索是准了，可检索到的片段模型读不懂。比如切出这么一段：

超出上述标准的部分由个人承担，特殊情况需提前报备。

「上述标准」是什么？它在另一个片段里。这段话单独看缺少必要信息，交给模型之后，模型只能推测，或者无法作答。 中文文档里这个问题格外明显 ，因为中文习惯用「该」「上述」「前款」这类指代词。一旦前文被切掉，片段就缺少指代对象，语义不完整。

第 2 篇讲的 overlap、结构化切分、上下文增强（把标题路径拼进片段开头），都是在 切分阶段 处理这件事。

chuank太大也不行，太小也不行，兼顾两边的做法是： 用小块去检索，用大块去生成。 检索走小片段，向量不被稀释，精度高；交给模型的是大片段，上下文完整，指代关系也齐全。两个目标各自用最合适的粒度，不再互相制约。

实现上，有四种做法，按成本从低到高。

1. 父子文档检索

一个 500 字的父块，切成 5 个 100 字的子块。 向量库里只存子块 ，每个子块记住自己的 parent_id 。父块不参与向量检索，单独放在一个按 id 取值的文档库里：命中子块之后，用 parent_id 把父块取出来交给模型。LangChain 的 ParentDocumentRetriever 就是这样拆的： vectorstore 存子块和向量， docstore 存父块全文。

文档库不必另起一套重的系统。常见做法是 PostgreSQL、Redis、MongoDB等，或者向量库里另开一张不参与 ANN 的表，按主键读取即可。不要把整段父块写入每个子块的元数据，因为同一父块被切成 5 个子块，原文就会存 5 遍。

同一段住宿标准被切成多个子块，一次查询可能同时命中其中两三个，需要按 parent_id 去重，否则，提示词里就会出现两份几乎一样的父块，重复占用 Token。下一篇讲组装时还会再遇到这个问题。

2. 句子窗口 / 按位置前后扩展

不一定必须预先切好「父块」。索引时只存小片段，元数据里记下它在原文中的起止位置；命中后按位置往前后各扩展若干字，把周围上下文一并取回。再细一层，按句子索引，命中后返回该句前后各 N 句，这就是 句子窗口检索（Sentence Window Retrieval） 。

它和 overlap 解决的是同一类问题，只是处理的时机不同：overlap 是切分时预先重叠一段，句子窗口是检索命中后再扩展相邻句子。适合叙述连贯的长文档，指代、转折不会断在边界上。窗口太大就退化成大 chunk，一般前后各 1～3 句即可。

3. 摘要索引原文

第三种给每个大块生成一段摘要， 用摘要做 Embedding，原文存在元数据里，命中后返回原文 。

这特别适合表格、代码、图片这类「本身不适合向量化，但能用自然语言描述」的内容。一张报销标准对照表直接 Embedding，向量里主要是数字和单元格，语义很弱；先生成一句「一线城市住宿每晚上限 800 元，二线 500 元」的摘要，检索就能命中，返回时再把整张表交给模型。

代价是每个大块多一次摘要生成。摘要一旦偏离原文，检索会偏到别的主题上去，所以摘要提示词要写死「只概括、不发挥」，跟前面查询改写「只补全不扩展」是同一个约束。

4. 多向量索引

同一思路再推进一步：给同一个块生成多个向量（原文、摘要、假设问题），任一命中即返回原文。

假设问题这个向量，其实就是把 HyDE 的思路做到了索引阶段：预先生成用户可能提出的问题，检索时问句对问句，比「问句对陈述句」更容易命中。FAQ 场景很有效。索引成本明显更高，一块要算三个向量、占三倍存储，当然，召回率提升也明显。
