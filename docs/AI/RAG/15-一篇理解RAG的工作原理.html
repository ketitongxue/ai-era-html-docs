15-一篇理解RAG的工作原理

前面三个模块，我们一直在解决「怎么把话说清楚」的问题：怎么调模型、怎么控制参数、怎么写提示词、怎么约束输出格式。

但有一类问题，提示词写得再漂亮也解决不了。

比如你们公司有一份内部的《差旅报销制度》，你问模型「出差住宿费上限是多少」，它不可能知道，因为这份文件从来没进过它的训练数据。再比如你问「我上个月那笔订单发货了吗」，它也不可能知道，因为那条记录只在你们的业务数据库里。

模块一讲知识截止日期时，我们说过一句话： 模型不知道的，你提供给它。 这一模块就是把这句话工程化。

这一篇先建立整体认知：RAG 到底在解决什么问题、它的两个阶段各干什么、一次完整的问答里数据是怎么流动的，以及一个很容易一开始就选错的问题。同样是「让模型掌握私有知识」，什么时候该用 RAG，什么时候该用微调或者干脆靠长上下文。

一、RAG 要解决的问题

先看看不做任何处理，直接把问题交给模型会发生什么。

你问：「我们公司出差住宿费的报销上限是多少？」

它立刻给出确定答案：「一线城市每晚不超过 600 元，二线城市不超过 400 元。」

这个回答的问题不在于数字错了，而在于 它完全不知道你们公司是什么规定，却仍给出确定答案。 那份《差旅报销制度》从来没进过它的训练数据，它没有任何依据，但它还是给了你一个精确的答案，而且语气非常确定。

这就是 幻觉（Hallucination） 。

为什么会这样？模块一讲原理时那句话，现在可以用上了：

模型不是去某个数据库里「查」答案，而是拿参数算「这个上下文后面接什么概率最大」。

它内部完全没有「我知道」和「我不知道」这两种状态，只有「接下来这段话怎么写才最像一段合理的回答」。而在无数篇真实的差旅制度里，「一线城市每晚不超过 600 元」这种句式和数字出现得极其频繁，所以它就理所当然的出现在了回答中。

模型不是在骗你，它是在做它唯一会做的事：生成下一个最可能的词。

怎么解决呢？既然它缺的是依据，那就把依据给它。

你把公司那份《差旅报销制度》整篇复制进提示词，再问一遍「住宿费上限是多少」。这次它答「一线城市每晚不超过 800 元」，跟制度原文一字不差。

注意这里发生了什么： 模型的能力一点没变，它还是在算「接哪个词概率最大」。 只是上下文里已经有那个真实数字了，此时照抄它，反而成了概率上最省力的续写方式。

到这一步，其实已经完成了一个手工版 RAG。

这就是 RAG（Retrieval-Augmented Generation，检索增强生成）的全部思想：

回答之前，先去外部知识里检索出相关资料，写入提示词，让模型基于这些资料作答。

换句话说，就是把 闭卷考试变成开卷考试 。

需要注意的是，正因为它的原理是「让正确答案变成最省力的续写」，所以它只能 降低 幻觉，不能根除。上下文里没有的、或者写得含混的，模型照样会编造。

RAG就这么简单？为什么还需要一整个模块几篇文章来介绍？因为手工复制这个做法，在真实环境中，有很大问题：

公司文档不是一份，是三千份，几百万字，全部放入会超出上下文窗口，即使放得下也消耗大量 Token、还会导致大模型返回变慢。

于是，问题就变成了： 怎么在几百万字里，自动找到跟这个问题最相关的那几段，放到上下文中。

二、索引阶段与查询阶段

上一节留下的问题是：怎么在几百万字里自动找到最相关的那几段。

顺着这个问题往下想一层，就会发现一件事： 这个「找」的动作，不可能等到用户提问的那一刻才从头做。

于是 RAG 就被切成了两个阶段：索引阶段和查询阶段。

索引阶段（Indexing）：

原始文档 PDF/Word ──▶ 解析为纯文本 ──▶ 切分为小片段（chunk） ──▶ 向量化 ──▶ 存入向量库

你把三千份文档一次性处理干净，切成小片段，每片转成一串能表达语义的数字（ Embedding ，本模块的第 3 篇细讲），存进 向量数据库 。这一步很慢，可能跑几个小时，但它跟用户提问无关，可以在夜间离线运行。

查询阶段（Query）：

用户提问 ──▶ 向量化 ──▶ 在向量库中检索 Top-K ──▶ 拼进提示词 ──▶ 调模型 ──▶ 带引用的回答

用户的问题也转成向量，去库里找「语义最接近」的几个片段，拼进提示词，调模型作答。这一步必须快，通常检索只占几十毫秒，主要耗时在模型生成上。

光看流程图还是抽象，我们拿开头那份《差旅报销制度》举例，看看具体的处理流程。

我们先来看索引阶段。

第一步，把 PDF 解析成纯文本。怎么解析？下一篇会讲。

差旅报销制度 v3.2
三、费用标准
3.1 住宿标准：一线城市每晚不超过 800 元，二线城市不超过 500 元。
3.2 交通标准：市内交通凭票据实报销，单次超过 200 元需附说明。
四、报销流程
4.1 报销时限：出差结束后 30 个工作日内提交，超期需部门经理审批。

第二步，切成小片段。为什么要切、按什么切，也是在下一篇讲，这里先按小节切：

片段 1：住宿标准：一线城市每晚不超过 800 元，二线城市不超过 500 元。
片段 2：交通标准：市内交通凭票据实报销，单次超过 200 元需附说明。
片段 3：报销时限：出差结束后 30 个工作日内提交，超期需部门经理审批。

第三步，使用Embedding 模型，将每个片段转成向量（具体本模块的第 3 篇细讲），连着原文一起存进向量库：

片段 1  →  [0.021, -0.113, 0.087, ... ] 
片段 2  →  [-0.045, 0.062, -0.009, ... ]
片段 3  →  [0.008, 0.134, 0.051, ... ]

到这里索引阶段就结束了。 注意向量库里现在存着两类数据：片段原文，和它对应的向量。 向量用来检索，原文用来拼进prompt发送给模型。

我们再来看查询阶段

用户问：「 去上海出差住酒店最多能报多少？ 」

第一步，用同一个 Embedding 模型把这句话也转成向量：

问题  →  [0.019, -0.108, 0.091, ... ]

第二步，拿这个向量跟库里每个片段的向量进行计算，看谁的语义最接近（怎么算，本模块的第 3 篇细讲）：

片段 1（住宿标准）  相似度 0.87   ← 最接近
片段 2（交通标准）  相似度 0.41
片段 3（报销时限）  相似度 0.33

这里需要解释下： 用户说的是「上海」「酒店」，片段 1 里写的是「一线城市」「住宿」， 字面上一个词都没对上 ，但它照样排到了第一名。

这就是向量检索和传统关键词检索最根本的差别： 它比的是语义，不是关键字。 如果用关键词搜「上海」，这份制度里完全没有「上海」两个字，一条都搜不出来。向量检索怎么做到靠语义来检索的，这个我们在本模块的第03篇中讲解。

第三步，把命中的片段拼进提示词。最终真正发给模型的，是这么一段普通文本：

[System Prompt]
你是企业制度问答助手。只能依据 <context> 中的内容回答，并在句末用 [编号] 标注依据。
若 <context> 中没有相关信息，回答「制度文件中未找到相关规定」，不要自行推测。

[User Prompt]
<context>
[1] 住宿标准：一线城市每晚不超过 800 元，二线城市不超过 500 元。
</context>

问题：去上海出差住酒店最多能报多少？

第四步，模型返回：

一线城市每晚不超过 800 元。[1]

顺便留意 System 里那两句约束： 只能依据 context 回答 、 没有就说没有 。这两句是 RAG 提示词的标配。少了它们，模型会把检索到的片段和自身的「常识」混在一起使用，你根本分不清哪句有依据、哪句是编造的。

从上面的过程，我们可以总结：

第一，向量库里存的不是「知识」，是「文本片段 + 它的向量」。 检索出来的东西一定是你当初存进去的原文，一个字都不会变。上面第三步拼进提示词的那句话，跟片段 1 完全一致。

第二，模型对向量库毫不知情。 你看第三步那段提示词，它就是一段普通文本，模型完全不知道有个数据库存在，也不知道这段资料是怎么来的。 RAG 全部发生在调模型之前，跟模型本身没有任何关系。 这一点想清楚了，你就不会问「怎么让 GPT 连接我的知识库」这种问题了。

第三，RAG 其实就六个关键步骤：解析、切块、向量化、向量存储、检索、上下文组装。 前四个在索引阶段，后两个在查询阶段。后面四篇要做的事，就是把这六个步骤的细节讲清楚。

三、RAG、微调和长上下文怎么选

「让模型掌握我们的私有知识」，技术方案不止 RAG 一条。这是面试常考的题。

方案一：微调（Fine-tuning）。 拿你的数据继续训练模型，把知识写进参数里。

这个方案听起来最彻底，但它有几个无法回避的问题：

  • 贵且慢。 准备数据、训练、评估，非常慢。知识更新一次就得重来一次。
  • 不可追溯。 知识融进参数里了，模型答错了你连是哪条数据导致错误的都查不出来，更无法修正。
  • 权限难以控制。 参数里的知识没法按用户区分，A 部门的数据训练进去了，B 部门的人一旦提问也能得到答案。
  • 微调主要改的是「风格和格式」，不是「事实」。 这是最关键的一条。

最后一条值得多说一句。微调的强项是让模型学会 怎么做 ：固定的输出格式、行业说话方式、特定的判断标准。想让它可靠地记住 具体事实 （某个金额、某个日期、某条条款），性价比极低，而且照样会记错。

方案二：长上下文。 模型窗口现在动辄上百万 Token，直接把整份文档放入上下文，不再检索。

对小规模知识（几万字以内、并且不常变），这确实是最简便的选择，不必仅为显得专业而引入向量库。但规模一大就难以维持：

  • 成本线性上涨。 每次提问都要为整份文档付输入 Token 的钱。哪怕有 Prompt Caching 打折，几百万字的成本负担也非常大。
  • 延迟明显变差。 输入越长，首字返回越慢。
  • 效果不一定更好。 模块一提到 Lost in the Middle：内容太长时，模型更容易漏掉夹在中间的信息。给它 50 页无关文档 + 1 段有用的，往往不如只给有用的那 1 段。

方案三：RAG。 每次只检索相关的几段。

  • 知识更新只需重跑索引，通常只需几分钟
  • 每次输入 Token 可控，成本和延迟稳定
  • 答案能标出来源，出错能顺着链路查
  • 权限可以在检索时按元数据过滤（需要额外记录元数据信息在向量数据库中，后面会讲）

RAG的代价是工程复杂度：解析、切分、Embedding 模型、向量库、检索质量调优、评测，一整套都得建起来。
