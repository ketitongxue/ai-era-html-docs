17-Embedding和向量数据库

上一篇，我们介绍了文档解析、切块（Chunk），已经得到一批结构清楚、带着元数据的文本片段。

接下来要做的就是给每个片段生成向量，并将向量、文本片段、元数据，一并存储入向量数据库，并提供检索能力。

也就是，我们前面讲的RAG六个关键步骤中的：向量化和向量存储这两个步骤。

一、Embedding 是什么

模块一讲原理时说过：模型只认数字，不认文字。每个词都要先翻译成一串数字，也就是向量；语义相近的词，向量距离也近。

Embedding 模型沿用了同样的思路，只是对象从「一个词」换成了「一整段文本」。

给它一段话，它返回一个固定长度的浮点数组，比如 1536 个数字。这串数字就是这段话对应的向量。意思接近的两段话，向量也会靠得很近。

curl https://api.openai.com/v1/embeddings \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "text-embedding-3-small",
    "input": "出差住酒店最多能报多少钱？"
  }'

返回的就是这段话的向量， embedding 字段是一个定长浮点数组（ text-embedding-3-small 是 1536 个数字，这里省略中间部分）：

{
  "data": [
    {
      "index": 0,
      "embedding": [-0.0121, 0.0338, -0.0074, 0.0192, -0.0455, ...]
    }
  ],
  "model": "text-embedding-3-small",
  "usage": {"prompt_tokens": 12, "total_tokens": 12}
}

注意两点： 不管输入是 5 个字还是 500 个字，输出的维度都一样 （这里是 1536）；那些数字本身没有任何人能读懂的含义，别试图解释第 x 维代表什么。

它唯一有意义的用法是 互相比较 。看这组数据（数值为示意）：

A: 出差住酒店最多能报多少钱？
B: 差旅住宿费的报销上限是多少？
C: 一线城市每晚不超过 800 元。
D: 公司年假怎么计算？

相似度（余弦）
A ↔ B   0.94   问法不同，意思几乎一样
A ↔ C   0.71   一问一答，相关但不同形态
A ↔ D  0.32   完全不同的话题

A 和 B 一个字都没重合，相似度却是 0.94。 这就是向量检索的价值：它匹配的是语义，不是关键字。

二、Embedding 模型

我们知道，大模型（GPT、DeepSeek 这些）的训练目标是 预测下一个词 ，而Embedding 模型的训练目标是 让语义相近的文本向量靠近、语义无关的文本向量远离 。做法是拿海量「相似文本对」和「不相似文本对」做对比学习。

Embedding 模型是专门为「比较」训练的独立模型，相比大模型，参数通常也小得多（几亿参数级别，推理更快、调用成本也更低）。

主流厂商大多顺带提供了 Embedding 模型：OpenAI 有 text-embedding-3-small / text-embedding-3-large ，Google 有 Gemini Embedding；国内阿里通义有 text-embedding-v3 、智谱有 embedding-3 。当然， 并不是每家做大模型的厂商都提供了 Embedding 模型。 比如 Anthropic（Claude）、DeepSeek、Kimi 就没有对外提供。

除了这些「大模型厂商顺带做的」，还有一批专门只做 Embedding 的团队，开源里名气最大的是 BGE（智源）和 E5 系列等。

在做Embedding模型的技术选型时，需要考虑最大输入长度、向量维度、部署方式。

最大输入长度。 常见是 512 或 8192 Token。 这个值必须和你的 chunk_size 对齐 ，超过部分会被静默截断，片段后半部分的信息没有进入向量，查询时也用不上被截断的这部分文字。

向量维度。 维度直接决定存储成本：500 万片段 × 1536 维 × 4 字节 ≈ 30 GB，换成 768 维就只要 15 GB。现在不少模型支持 降维输出 （OpenAI 的 dimensions 参数、BGE-M3 等），可以在精度损失很小的情况下减少约一半存储，数据量大时值得推荐。

部署方式。 当然，直接调用云厂商的 API 最简单，但每一次索引和查询都要发一次网络请求，数据也要出内网。因为Embedding模型要比大模型小很多，私有化部署一个开源 Embedding 模型（比如阿里的 Qwen3-Embedding ，提供 0.6B / 4B / 8B 多个尺寸），一张消费级显卡就能跑起来，对数据敏感的企业场景通常是更好的选择。

最后，我们强调一下，不同的Embedding模型对同一段话计算出来的向量是不同的，因此，如果你用OpenAI的Embedding模型 text-embedding-3-small 去构建向量数据库，那么，查询的时候，也需要使用 text-embedding-3-small 对查询计算向量。这样再计算相似度才有意义！

三、相似度怎么算

文本已经变成向量了，检索就只剩下一件事：把用户的问题也做成向量，去库里找离它最近的那几个片段。

Embedding 把「语义相似」翻译成了「几何距离」。 于是「找意思接近的文本」这个需要理解力的问题，变成了一道比较远近的数学题。

常用的算法有三种：

  • 余弦相似度（Cosine Similarity） ：看两个向量的夹角，只管方向不管长度。范围 -1 到 1，越大越相似。
  • 点积（Dot Product） ：对应位置相乘再求和，同时受方向和长度影响。
  • 欧氏距离（L2） ：两点之间的直线距离，越小越相似。

这里重点把 余弦相似度 讲一下，因为它是文本检索里最常用的一种。

它的核心就一句话： 只看两个向量的方向夹角，完全不管长度。 夹角越小，方向越一致，就越相似。

  • 夹角 0°（方向完全一致）→ 余弦值 = 1，最相似
  • 夹角 90°（互相垂直、毫不相关）→ 余弦值 = 0
  • 夹角 180°（方向完全相反）→ 余弦值 = -1

计算公式是「点积除以两个向量各自的长度」：

cos(θ) = (A · B) / (|A| × |B|)

举个例子。为了直观，我们用二维向量（真实向量是几百上千维，但道理完全一样）：

P = [1, 1]   Q = [2, 2]   R = [1, 0]

先算 P 和 Q 的余弦相似度：

点积 P·Q = 1×2 + 1×2 = 4
|P| = √(1²+1²) = √2    |Q| = √(2²+2²) = √8
cos = 4 / (√2 × √8) = 4 / 4 = 1

P 和 Q 方向完全相同（都指向右上 45°），所以余弦相似度是 1，尽管 Q 的长度是 P 的两倍。 长度不影响结果，这恰恰是我们想要的 ：同一句话说一遍和连说三遍，语义没变，我们不希望它因为「更长」就被判成另一个意思。

再算 P 和 R 的余弦相似度：

点积 P·R = 1×1 + 1×0 = 1
|P| = √2    |R| = 1
cos = 1 / (√2 × 1) ≈ 0.71

P 指向 45°、R 指向 0°，夹角 45°，余弦约 0.71，方向相关，但并不重合。

回头看前面那组 A/B/C/D 里 0.94、0.71、0.32 这些数字，就是这么算出来的，只不过维度从 2 变成了 1536。

四、向量数据库

有了向量和相似度算法，你可能会觉得：

直接把向量和文本片段，存储到MySQL数据库里，拿到一个查询之后，就跟库里每条向量都算一遍相似度、再排个序？不就行了，为什么需要向量数据库呢？

这种「全部算一遍再排序」的做法叫 暴力检索 ，结果绝对精确，小规模下也确实够用。

问题出在大规模数据上。如果数据库中存储了500 万个片段，每来一个查询都要算 500 万次相似度，耗时是不可接受的。

所以大规模检索要换做法： 近似最近邻检索（ANN，Approximate Nearest Neighbor） 。它事先把全量向量编成一套索引（常见是 HNSW 这类图索引）。查询时不再跟每条向量逐个比对，而是顺着索引走到目标附近，只跟一小撮候选比较。

名字里的「近似」体现了它的特点：

它不保证一定找到最相似的那几个，只保证极快地找到「大概率是最相似的那几个」。

也就是说，ANN意味着 检索结果天生就有一定的丢失概率 。当你发现某个明明存在的片段没被检索到时，除了 Embedding 效果不好，也可能就是 ANN 漏了。

向量数据库 存在的意义是除了最基本的向量存储和ANN检索之外，还打包了这一整套功能，让你不用自己从零开发。具体来说，包含以下功能：

  1. 向量存储 + 索引 ，这是基础
  2. 元数据过滤 ，跟向量检索配合使用
  3. 增删改查和索引更新 ：文档更新时能精确删除、更新某些片段，还要能保证增量写入后索引依然有效
  4. 持久化与恢复 ：重启不丢数据，能备份能回滚
  5. 横向扩展 ：分片、副本、高可用
  6. 混合检索 ：同时支持向量检索和关键词检索并融合结果（下一篇会讲）

常用的向量数据库有哪些

市面上叫「向量数据库」的产品有几十种，但大致就三类。

第一类，在已有数据库上加装向量能力。

  • pgvector ：PostgreSQL 的一个扩展。装上之后，PostgreSQL 就多了一个 vector 字段类型和配套的 ANN 索引。最大的好处是 业务数据和向量存放在同一个库里 ，一条 SQL 就能同时做元数据过滤和向量检索，事务、备份、权限这些全都复用你现成的那一套，不用再单独维护一个系统。
  • Elasticsearch ：如果你本来就用 ES 做全文检索，那它从 8.x 起就自带了向量检索（底层也是 HNSW）。它的优势是天然支持 混合检索 ：关键词和向量同时检索，再融合结果（下一篇会专门讲）。

第二类，专业向量数据库。 这类是专门为向量检索从头设计的，功能和性能上限最高，代价是要单独部署和运维。

  • Milvus ：开源，功能最全，面向亿级、十亿级向量存储设计，支持分布式、多种索引类型。规模大、要求高时的首选，但运维也最重。
  • Qdrant ：Rust 写的，性能好、部署轻，单机就能支撑相当大的数据量，元数据过滤能力强，这两年上升很快。
  • Chroma ：最轻量的一个， pip install 就能用，甚至能直接嵌进你的 Python 进程里跑。适合本地开发、写 demo、跑原型。

第三类，云服务。 国外最有名的是 Pinecone ，不用自行承担运维，开箱即用、按量付费。国内各大云厂商也都有对标产品：阿里云的 DashVector 、腾讯云的 向量数据库（Tencent Cloud VectorDB） 、火山引擎的 VikingDB 等。这类服务共同的优点是运维负担低，代价是数据托管在别人那里、成本随规模上涨。

那到底怎么选？一句话：按现状选，不要一开始就选功能最全、运维最重的。

  • 已经在用 PostgreSQL → 直接用 pgvector，百万级通常够用，还少维护一个系统。
  • 已经在用 Elasticsearch → 用它自带的向量能力，同时就能做混合检索。
  • 只是本地开发、跑原型 → Chroma，几行代码即可运行。
  • 数据量到了亿级、要高并发低延迟 → 这时候才值得引入 Milvus、Qdrant 这类专业向量库，或者干脆用 Pinecone 托管。

最后有一条经验，比「选哪个库」更重要： 别把某个向量库的原生 API 直接散落在业务代码里，用一层自己的接口把它包起来。

不管你今天选了哪个，随着数据量增长、需求变化， 迁移几乎是必然发生的事 。今天 pgvector 够用了，明天数据涨到上亿就得换 Milvus。如果你的写入、检索、删除全都直接调某个库的原生方法，那么一旦迁移，所有调用都要改；而如果一开始就定义好一组自己的接口，业务代码只依赖这层抽象，换库就只是换一个实现类的事，上层代码一行都不用动。

模块五讲框架时，会看到 Spring AI 和 LangChain 都内置了这层抽象。
