20-RAG评测与数据权限

前面五篇文章已经把 RAG 的六个步骤讲完了：解析、切分、向量化、向量存储、检索、上下文组装。

到这里，一个能跑起来的 RAG 系统已经成型，你问一句，它能带着引用回答你。

但「能跑起来」和「能交付上线」之间，还差两件事。

第一件是评测。RAG搭建不是一蹴而就的，很多时候，需要不停的调整优化，比如调整片段的长度、切分方法、切换 Embedding 模型、上混合检索、优化提示词等等。 没有评测集，所有的优化都是凭感觉。 改完拿三个问题试一试，觉得「好像好了一些」就上线，这是很多团队的真实状态。

第二件是数据权限。举个例子。公司知识库里既有面向全员的规章制度，也有 HR 那份只给管理层看的调薪方案，它们被切成片段之后，存进同一个向量库里。这时候一个普通员工问一句「今年调薪是按什么标准定的」，检索环节如果不带权限过滤，向量库就会直接把不该泄露的调薪方案捞出来给员工看。

这篇文章我们就来讲评测和权限。

一、评测分两阶段进行

先看一下这样一个场景。

你把片段从 500 字改成 300 字，把整个知识库重新构建了一遍，拿几个问题试了试，觉得答得更准了，而上线之后，用户投诉系统没有以前好用了。

问题不在于谁的感觉更准，而在于 你们手上没有一套评测标准 。即固定一批问题、固定一套判定标准，改动前后各跑一遍，好坏由结果判定。

这就有点像性能基准测试，代码优化了，理论上主观感觉变快，但这并不可靠，得跑一下基准测试，得出的结论才更可靠！

对于RAG来说，它的”基准测试“该如何设计呢？

我们要评的是整条链路的最终结果，也就是用户看到的那句回答准不准。而一句回答要准，中间有两个环节都不能出错：先得把该用的那段资料检索回来；资料拿到之后，模型还得严格按资料回答，不能自行补充资料中没有的内容。

前半部分，我们称作”检索“；后半部分，我们称作”生成“。 我们需要为检索和生成两个阶段，分别设计评测方案。

我们再举个例子解释下。

用户问「一线城市住宿能报多少」，系统答「大约 500 元」，而制度里写的是 800。同样一次答错，导致的原因可能并不相同：

  • 检索完全没有把「3.1 住宿」那一段捞回来，模型手上没有资料，只能凭空编造一个数字；
  • 资料捞回来了，白纸黑字写着 800，是模型自己写成了 500。

虽然从用户角度来看结果都一样，但是，开发者需要对不同的环节进行优化。前者需要优化”检索“阶段，后者需要优化”生成“阶段。

相对应的，我们也要为两个阶段设计不同评测方案和评测数据集。

二、检索质量评测指标

要判断检索对不对，得先知道「对」长什么样。

评测的第一项工作就是： 给每个测试问题标注出「答案到底落在哪几个片段里」 ，这些片段业内叫 黄金片段（Golden Chunk） 。没有它，下面所有检索评测指标都无从算起。标注这件事听起来很繁琐（需要人工），其实有省力的办法，后面再讲。

标好之后，评测检索质量的指标就变成了： RAG检索捞回来的 Top-K 里，到底有没有黄金片段？

这就是 Hit Rate（命中率） 。有就记 1 分，没有记 0 分。假设测试集里有三个问题，检索都取 Top-5：

问题 1 的回答：黄金片段排在第 1 位             →  1
问题 2 的回答：黄金片段排在第 3 位             →  1
问题 3 的回答：Top-5 里根本没出现黄建片段       →  0

Hit Rate = (1 + 1 + 0) / 3 = 0.67

它非常直观，也最该先被纳入评测，毕竟检索未命中，后续生成无从谈起。

但 Hit Rate 只回答「在不在」，不回答「排第几」。 问题 1 回答的黄金片段排第 1、问题 2 回答的黄金片段排第 3，在它眼里都是 1 分；哪怕掉到第 20 位，只要还在候选范围里，分数仍是 1。本模块第 4 篇讲过，召回阶段放宽到几十条，重排序之后最终写入提示词的只有 3 到 5 条，排在第 20 的片段根本不会被选中。

于是需要第二个指标 MRR（Mean Reciprocal Rank，平均倒数排名） 判定是否把黄金片段排在前面。

MRR的计算方法很简单，找到黄金片段的排名，取倒数，再对所有问题求平均。

还是上面那三道题：

问题 1：黄金片段排在第 1 位     →  1/1 = 1.00
问题 2：黄金片段排在第 3 位     →  1/3 = 0.33
问题 3：Top-5 里根本没出现      →  0

MRR = (1.00 + 0.33 + 0) / 3 = 0.44

因为取的是倒数，名次往后掉一位，分数下降非常明显。这正是我们要的效果： MRR 对「有没有排到最前面」极其敏感 。

起步阶段， Hit Rate 和 MRR 两个已经足够 。后续为了精细化，可以再补充另外三个指标。

第一个是 Recall（召回率） ，它衡量的是「该捞的捞全了没有」。它和 Hit Rate 的区别，只在答案分散于多个片段的题目上才体现得出来。

比如「差旅报销都有哪些费用标准」这道题，答案得靠住宿、交通、伙食三段拼起来：

黄金片段：c17（住宿）、c23（交通）、c31（伙食）
Top-5 捞回：c17、c05、c88、c23、c42

Hit Rate = 1            （命中了，这个指标看不出问题）
Recall   = 2/3 ≈ 0.67   （伙食那段没捞到，模型手上的资料是残缺的）

模型拿着这份残缺的资料，要么漏答一项，要么自己补一句。所以多跳问题、以及这类需要综合几段才能回答的问题，必须看 Recall。

第二个是 NDCG（归一化折损累计增益） ，它衡量的是「该靠前的有没有靠前」。

检索回来的片段，相关程度并不一样：有的能完整回答问题，有的只沾一点边。把最能回答问题的那段排在第 1 位，和把它挤到第 3 位、前面塞两段半相关的，对后面生成的影响完全不同。

NDCG 的名字拆开就是三步。 增益 是按相关程度给每条结果打分，完全能回答记 2，部分相关记 1，无关记 0； 折损 是越靠后越不值钱，第 1 位不打折，第 2 位除以 1.58，第 3 位除以 2（对应 log₂(2)、log₂(3)、log₂(4)，这是业内的打折惯例）；把打折后的分数加起来，就是折损累计增益。 归一化 则是拿这个数除以「理想排法」的得分，得分范围归一化为 0 ~ 1，不同题目才能放在一起比较。

两个系统捞回的是同样三段，只是顺序反了过来：

系统 A 的前 3 条：[2, 1, 0]   （完全相关、部分相关、无关）
系统 B 的前 3 条：[0, 1, 2]   （同样三段，顺序倒过来）

按位置打折后累加：
A = 2 + 1/1.58 + 0   = 2.63
B = 0 + 1/1.58 + 2/2 = 1.63

最理想的排法就是 A 这样，得分 2.63，拿它当分母：
NDCG(A) = 2.63 / 2.63 = 1.00
NDCG(B) = 1.63 / 2.63 = 0.62

同样的三段资料，仅仅因为排序不同，分数就从 1.00 掉到了 0.62。

第三个是 Context Precision（上下文精确率） ，前面几个指标都在关心「该给的给了没有」，它关心的是反面： 混入了多少无关内容。

Top-5 捞回 5 段，其中只有 2 段跟问题真的相关
Precision = 2/5 = 0.4

也就是说，六成的上下文 Token 花在了噪声上。增加费用还在其次，更麻烦的是稀释模型的注意力。

三、生成质量评测指标

资料给对了，工作只完成了一半，接下来得看模型有没有利用好这些资料。

第一个也是最重要的一个： 忠实度（Faithfulness） ，答案里的每一条断言，是不是都能在检索到的资料里找到支持。

它怎么算？上一篇讲二次核验时那套「把答案拆成一条条独立断言，再逐条回去问大模型这个断言资料支不支持」的流程，也可以用在这里：

资料：[1] 一线城市每晚不超过 800 元，二线城市不超过 500 元。

答案：「一线城市住宿每晚不超过 800 元 [1]，超出的部分可以凭发票申请补贴。」

拆成断言，逐条回去核验：
  1. 一线城市住宿每晚上限 800 元      →  SUPPORTED
  2. 超出部分可以凭发票申请补贴        →  NOT_ENOUGH（资料里根本没提这回事）

忠实度 = 1 / 2 = 0.5

第 2 条就是典型的幻觉：读起来合情合理，甚至比原规定更完整，可资料里完全没有这句话。 忠实度跟幻觉率相对，是生成侧最优先关注的指标。

但忠实度高不等于答得好，它只衡量「有没有编造」，不管是否回答了用户的问题，比如：

用户问：一线城市住宿能报多少？

答案：「差旅报销需在回程后 15 天内提交，并附上发票和审批单 [2]。」

每句话都有依据，忠实度满分，可它答的不是用户问的问题。这种「句句有依据、就是没回答问题」的情况，要靠 答案正确性 来判定，也就是拿答案跟标准答案比对得出的。

再往下是 引用准确率 。编号合法、结论也对，只有依据挂错了地方。比如：

资料：[1] 一线城市每晚不超过 800 元…
     [2] 市内交通单次超过 200 元需附说明

答案：市内交通单次超过 200 元需附说明 [1]。

结论没错，编号也确实存在，但依据其实在 [2] 里，[1] 讲的是住宿。

最后是 无答案准确率 。

  • 知识库里没有，模型在没有依据时仍给出了答案。这是 假阳性，线上最危险的一类失败 ，用户会拿着一条编出来的规定去办事。
  • 知识库里有，模型却说「未找到」。这是假阴性，不危险，但次数一多，大家就不再信任这个系统了。

所以，这个指标要分两个方向统计，假阳性那一侧：

测试集里 20 条「知识库中确实没有答案」的问题：
  17 条明确回答了「知识库中未找到相关规定」
   3 条编出了一条像模像样的规定                  ← 假阳性

无答案准确率（假阳性方向）= 17 / 20 = 0.85

假阴性那一侧：

测试集里 20 条「知识库中确实有答案」的问题：
  16 条给出了基于资料的回答
   4 条却说「知识库中未找到相关规定」            ← 假阴性

无答案准确率（假阴性方向）= 16 / 20 = 0.80

四、如何根据指标做优化

指标的价值不在于写一份好看的测试报告，而在于它能告诉你下一步该优化哪里。

现象 说明什么 该动哪里
Hit Rate 低 完全没有捞到 数据解析和切分、混合检索、查询改写
Hit Rate 高但 MRR 低 捞到了但排在后面 重排序
检索指标都好，忠实度低 资料给对了，模型在编 提示词约束、降温度、缩短上下文、换模型
忠实度高但正确性低 忠实地照抄了错资料 知识库本身有过期或错误内容
无答案假阳性高 没有依据仍给出答案 检索 Top-K 过滤阈值、提示词里的无答案指令、输出层校验
无答案假阴性高 有却说没有 阈值太严、召回不足

其中，忠实度、答案正确性这类指标，没有标准答案可对比，只能让另一个大模型来当裁判，也就是前面讲到的 模型裁判（LLM-as-a-Judge） 。

这套判定逻辑不用自己从零写，社区已经有几个现成的框架。

RAGAS 是 RAG 评测里用得最多的一个。 它是个 Python 库，把前面讲的这些指标都实现好了，你只要按它的格式准备数据：每条样本包含问题、检索回来的片段、系统给出的答案，以及可选的标准答案。

from ragas import evaluate
from ragas.metrics import (
    faithfulness,        # 忠实度：答案里的断言在资料里有没有依据
    answer_correctness,  # 答案正确性：跟标准答案比对
    context_precision,   # 上下文精确率：捞回来的片段有多少是真有用的
    context_recall,      # 上下文召回率：该捞的片段捞全了没有
)

result = evaluate(
    dataset,             # 每条样本：question / contexts / answer / ground_truth
    metrics=[faithfulness, answer_correctness, context_precision, context_recall],
    llm=judge_llm,       # 裁判模型，记得换一家厂商，比如 qwen3.8-max
    embeddings=embed_model,   # 算答案正确性里的语义相似度要用
)

这里有个容易被忽略的成本问题： RAGAS 的每个指标、每条样本都要调用一次甚至多次裁判模型。 50 条样本配 4 个指标，一轮评测就是几百次调用。所以裁判不要默认用最贵的档位，判断题交给 gpt-5.6-luna 、 deepseek-v4-flash 这类便宜模型通常已经足够。

五、测试集从哪来

讲完怎么评测，剩下最后一个问题：测试集如何准备。

其实，测试集不必一开始就准备几千条，上一模块讲提示词评测的时候，提到： 30 到 50 条有代表性的样本，就已经远好于只手工试三条。 那个结论在 RAG评测里同样适用。

不过， RAG评测比提示词评测多一道工序： 得标黄金片段 ，因为，检测质量指标大都依赖它。

这道工序看起来很繁琐，需要人工来做，其实不然，有自动化的办法：**反过来，让模型根据chunk出题。**题目是从哪个 chunk 生出来的，哪个 chunk 就是这道题的黄金片段。

GEN_PROMPT = """根据下面这段资料，提出 2 个用户可能会问、且答案完全在这段资料内的问题。
问题要口语化、像真实用户的问法，不要出现「根据这段资料」这类表述。
同时给出简短的标准答案。输出 JSON 数组：[{"question": ..., "answer": ...}]

资料：{chunk}"""

这种方法能快速生成出几百条带标注的样本。当然， 必须人工筛一遍。 筛完再按类别配比，让测试集中的样本更加丰富：

类别 占比 为什么必须有
常规问答 40% 最基本的
无答案问题 20% 最容易被漏
多跳 / 需要多个片段 15% 暴露召回不足
精确编号、型号、缩写 10% 检验混合检索有没有真的生效
表格和数值 10% RAG 最难解决的场景
注入攻击样本 5% 检验间接注入防护

并不是所有的样本都可以通过自动的方式生成，比如无答案样本，因为 它没法从文档反向生成。 文档里有的内容，生成不出「知识库里没有」的问题，这部分测试样本只能人工来编造。

除了自动生成、人工编造测试样本之外， 线上每修一个 bad case，就往测试集里沉淀一条。 在上一模块，讲提示词测试集的构造时，也提到过类似的方法。

六、数据权限

回到开篇那个例子：普通员工问一句调薪方案，RAG 就把管理层文档的内容读了出来。如何解决这个问题呢？

最简单的方案是 后置过滤 ：在经过RAG检索、重排序等一系列操作，得到 Top-5 个片段，在拼入提示词之前，把用户无权访问的片段过滤掉。但是，这种方案有一定问题，比如：

正确的做法是 前置过滤 ：把权限作为过滤条件一起发给向量库，让它只在这个用户有权访问的片段范围内做近邻搜索。这样返回的 5 条，是「他能看的资料里最相关的 5 条」，一条都不浪费。

要做前置过滤，前提是向量库里的每个片段都带有访问控制信息，也就是本模块第 2 篇讲元数据时记录的那个 acl 字段，在这里用上了：

# HR 那份调薪方案切出来的片段
{
    "chunk_id": "policy-salary-2026#c04",
    "text": "2026 年度调薪面向 P6 及以上员工，调薪幅度区间为……",
    "doc_title": "2026 年度调薪方案",
    "source_url": "https://wiki.internal/hr/salary-2026",

    "acl": ["hr", "exec"],        # 只有 HR 和管理层能看
}

# 对照一份全员可见的制度，它的片段长这样
{
    "chunk_id": "policy-travel-2026#c17",
    "text": "一线城市每晚不超过 800 元，二线城市不超过 500 元。",
    "doc_title": "差旅报销制度",
    "source_url": "https://wiki.internal/policy/travel",

    "acl": ["all_staff"],         # 全员可见
}

用户这一侧同样是一组角色标签，比如财务同事的 user.roles 是 ["all_staff", "finance"] 。两边一求交集，就能知道有没有权限查看了。

落到代码上，以 Milvus 为例：

# 只有用户的任一角色出现在片段的 acl 里，这个片段才进入检索范围
results = client.search(
    collection_name="kb",
    data=[q_vec],
    filter="ARRAY_CONTAINS_ANY(acl, {roles})",   # 前置过滤，跟着检索一起下推
    filter_params={"roles": user.roles},          # 用参数占位，别拿字符串拼表达式
    limit=5,
    output_fields=["text", "doc_title", "source_url"],
)

filter 里那句表达式不是拿到结果之后再执行的，Milvus 会把它和向量检索一起做，只在符合条件的片段里做近邻搜索。

元数据的条件过滤各家写法不一样，pgvector 是 SQL 里多一个 WHERE 条件，Elasticsearch 是 filter 子句，但思路完全一致。
