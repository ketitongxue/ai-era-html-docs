16-从原始文档到可检索知识库

上一篇举例的时候，我拿了一份排版规整的《差旅报销制度》，解析出来是干净的纯文本，按小节一切就成了三个语义完整的片段。

真实项目往往没那么简单了。你拿到的文件格式可能各式各样：Markdown、PDF、扫描版PDF、Word等。

这一篇就详细讲RAG构建的第一个步骤：文档的解析和抽取。

先给一个结论，好让你重视这一步：

RAG 效果不好，大多数问题出在数据处理，而不是模型或者检索算法。

切坏一个表格、丢掉一个章节标题、漏掉一条元数据，后面即使换更强的模型，也很难补回。 Garbage in, garbage out，在 RAG 里体现得格外明显。

一、文档解析

文档解析就是把各种格式的文件变成纯文本。

Markdown、TXT、代码文件 最容易处理，本身就是纯文本，还自带结构，是 RAG 最友好的输入。

Word 本质是个 zip 包着的 XML，能拿到标题层级和表格结构，比 PDF 好处理得多。

PDF 最麻烦，也是最常用的文档格式，因此，我们重点说下它。

PDF 记录的是「哪个字符画在页面的哪个坐标」，它本身没有「段落」「标题」「表格」这些概念。所有结构都得靠解析器根据坐标去猜。

于是通常会遇到这些问题：

  • 双栏排版被读成一行。 学术论文、产品手册很常见。解析器按 Y 坐标扫过去，把左栏第一行和右栏第一行拼成了一句话，读出来的文本完全是乱的。
  • 表格解析丢失对应关系。 表头和数据的对应关系没了，「800」还在，但你不知道它是住宿标准还是交通标准。
  • 跨页段落被切断。 一句话从第 3 页末尾延续到第 4 页开头，按页解析就断成了两半。
  • 扫描件根本没有文字层。 PDF中的内容是图片，解析出来的文本是空的，必须先做 OCR 才行。

当然，对于大部分开发者来说，都不可能从零手写代码去解决这些问题，而是找到合适的现成的工具。工具选型无外乎看这个工具，是否能处理复杂版面，是否具备OCR能力（针对扫描件）等。

如果你用 LangChain4j 或 Spring AI，很多工具库都已经集成好了，不用自己对接。

Spring AI 提供 spring-ai-tika-document-reader （全格式，利用 Apache Tika 从 PDF、DOC/DOCX、PPT/PPTX、HTML 等多种格式中提取文本）、 spring-ai-pdf-document-reader （底层 PDFBox，含按页切的 PagePdfDocumentReader 和按 PDF 目录切段的 ParagraphPdfDocumentReader ）、 spring-ai-markdown-document-reader ，HTML 有 JsoupDocumentReader 。

LangChain 生态比 Spring AI 丰富得多，有大量社区加载器（Document Loader）。常用的有这样一些：

  • PDF ： PyPDFLoader （底层 pypdf 工具，速度快，复杂版面容易乱）、 PyMuPDFLoader （底层 PyMuPDF 工具，速度和文本质量兼顾，日常首选）、 PDFPlumberLoader （能抽表格，但慢一些）、 UnstructuredPDFLoader （底层 unstructured 工具，支持版面分析和OCR）
  • Word / PPT / Excel ： Docx2txtLoader （只要纯文本时最简便）、 UnstructuredWordDocumentLoader （保留标题、列表、表格结构）、 UnstructuredPowerPointLoader 、 UnstructuredExcelLoader
  • 网页与 Markdown ： WebBaseLoader 、 BSHTMLLoader 、 UnstructuredMarkdownLoader

除此之外，AI 的发展，还促生了一批 AI 原生解析器。

它们的思路和传统解析器完全不同： 不再靠字符坐标去猜结构，而是先用视觉模型做版面分析 ，把页面切成标题、正文、表格、图片、公式这些区块，判断出正确的阅读顺序，再逐块转成文本，最后输出带结构的 Markdown 或 JSON。双栏、表格、公式这些传统解析器难以处理的地方，恰好是它们的强项。

常见的有这么几个：

  • MinerU ：上海人工智能实验室开源，对中文文档和公式的支持是这批工具里最好的之一，可以本地部署，国内项目用得很多
  • Marker ：开源，专做 PDF 转 Markdown，速度快、输出干净，学术论文场景口碑不错
  • Docling ：IBM 开源，支持 PDF/DOCX/PPTX 等多种格式，表格结构还原做得比较细
  • Unstructured ：既是开源库也提供云服务，格式覆盖最全， hi_res 模式会调版面模型

开源方案需要自己部署，需要使用 GPU，纯 CPU 上跑一页要几秒到几十秒，小规模试用不易察觉，等到批量导入几千份文档，这个差距会被放大。因此，除非你的项目的核心功能就是跟文档处理强相关的，不然，一般项目用不上。

其实，很多云厂商都提供了文档智能服务 ：阿里云文档智能、腾讯云文档识别、百度智能文档分析、Azure AI Document Intelligence、Google Document AI，开箱可用、自带 OCR，是大部分项目的首选，当然，缺点是文档要出内网，涉密场景一般不适合。

对于实在处理不了的复杂文档，我们还可以调用支持多模态的大模型，比如 gpt-5.6 、 qwen3.8-max 等，直接把页面图交给模型识别。但缺点也比较明显：成本高、速度慢。

二、元数据

上一节，我们提到，存到向量数据库中的有向量和原文片段，向量是为了查询，原文片段是为了拼进Prompt。其实，除了这两个信息，向量数据库中还会存储 元数据（Metadata） ，它看似可有可无，实际很有必要！

一个够用的元数据结构大概是这样：

{
    "text": "一线城市每晚不超过 800 元，二线城市不超过 500 元。",

    # 溯源用：回答里要给出引用，出错要能查到原文
    "doc_id": "policy-travel-2026",
    "doc_title": "差旅报销制度",
    "source_url": "https://wiki.internal/policy/travel",
    "page": 3,

    # 结构用：片段在文档中的位置
    "heading_path": "差旅报销制度 > 三、费用标准 > 3.1 住宿",

    # 过滤用：检索时先按条件缩小范围
    "doc_type": "制度文件",
    "department": "HR",
    "effective_date": "2026-01-01",
    "version": "v3.2",

    # 权限用：不同的人看到的资料不同
    "acl": ["all_staff"],
}

上述示例展示了元数据的四个用途：

溯源。 用户问「住宿费多少」，你答「800 元」，必须能点开查看原文，用户才能信任回答。这是 RAG 相对微调最大的优势。

过滤。 用户问「今年的报销标准」，你希望只在 effective_date >= 2026-01-01 的文档里检索，就可以使用元数据过滤。

权限。 如果检索时不带权限过滤，一个普通员工问「公司薪酬结构是怎样的」，向量库会把 HR 的机密文件检索出来并返回。

结构。 heading_path 这个字段的价值很大，下一小节讲切分的时候会专门说。

这里重点说明两点问题：

第一，元数据必须在解析和切片阶段就一并整理。

page 、 heading_path 这些字段，只有解析和切分的时候才知道。等文本已经切成一批片段并写入库中，你没法再倒推某段话原来在第几页、属于哪个小节。

第二，要区分「参与向量化的字段」和「只用于过滤的字段」。

有人把整个元数据 JSON 一起塞进待 Embedding 的文本里，结果 version 、 acl 这些和语义毫无关系的字段干扰了向量方向。原则是： doc_title 、 heading_path 这类本身带语义的字段，可以拼进文本参与向量化；其余的只存成字段，只用于过滤。

三、切块（Chunk）

为什么必须切块呢？主要有三个原因：

上下文窗口和 Token 预算装不下整份文档；Embedding 模型本身有输入长度上限；更重要的是， Embedding 一次只能给一段文本算出一个向量。 整份长文档往往同时讲住宿、交通、审批很多件事，全压进这一个向量里，每个主题都被其余主题冲淡了。用户问「住宿标准」，这份文档的向量既不像住宿，也不像交通，跟具体问题对不上，检索精度极差。

因此，切分的目标可以用一句话概括：

让每个片段自身语义完整，并且只讲一件事。

常用的切分方法有四种：固定长度切分、递归字符切分、结构化切分、语义切分。接下来，我们依次看下。

1. 固定长度切分

最简单的办法：不管句子、不管段落，数到第 500 个字就切一刀。

优点是实现简单，每段多长完全可控。但缺点很致命：它完全不管语义，经常把一句话从中间切断。比如原文是「一线城市每晚不超过 800 元」，硬切之后可能变成两段，前一段停在「一线城市每晚不超过」，后一段开头是「800 元」。单独看任何一段都缺信息，检索和回答都会出问题。

2. 递归字符切分：多数实际项目的默认选择

固定长度切分的致命问题，是断点完全不看语义，经常一句话切成两半。递归字符切分就是在优化断点：先尽量停在段落、句子这些自然边界上，实在找不到合适的边界，再退回去硬切。

具体做法是给一组 优先级从高到低的分隔符 。先按空行切成段落；某一段还是超过 500 字，再按换行切；还是太大，再按句号、问号切；一直切到够短为止。到最后都找不到标点，才退化成按字符硬切。

所以它叫「递归」：不是只切一次，而是对仍然超长的块，拿下一档分隔符再切一遍。一份差旅制度里，「住宿标准」那一节如果本身不到 500 字，就会整节留下来；「审批流程」那一节如果写得很长，才会继续按句切开。这样大多数片段都能在句子或段落的边界断开，不会再把「不超过」和「800 元」劈成两半。

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=80,
    # 优先在段落处断开，其次句号，最后才退化到硬切
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
)
chunks = splitter.split_text(text)

注意 separators 这个列表： 默认配置是给英文写的 。中文文档如果不改这一项，切分器几乎找不到该断的地方，最后会退化成跟固定长度切分差不多。这是中文 RAG 里最常见、也最容易被忽略的一个坑。

3. 结构化切分

如果文档本身有清晰结构，按结构切是最优的。

  • Markdown / HTML：按标题层级切，一个小节一个片段
  • 法律、制度文件：按「第 X 条」切，条款天然是完整语义单元
  • FAQ：一问一答一个片段，这是 RAG 最理想的数据形态
  • 代码：按函数、按类切

结构化切分最大的收益，是能顺手把标题路径带进片段里。

我们看这个片段：

一线城市每晚不超过 800 元，二线城市不超过 500 元。

它有两个问题：不知道说的是什么费用，也不知道是哪家公司哪一年的规定。用户问「差旅住宿标准」，这个片段的向量里并不包含「差旅」「住宿」这两个词的语义，很可能检索不到。

把标题路径拼上去，检索命中率立刻提升一档。这个做法叫 上下文增强（Context Enrichment） ，成本几乎为零，收益却很高。

差旅报销制度 > 三、费用标准 > 3.1 住宿标准
一线城市每晚不超过 800 元，二线城市不超过 500 元。

4. 语义切分

前面三种方法，断点都是看「形式」：数到多少字、遇到什么标点、标题在哪里。语义切分换了个依据：看「意思变没变」。

做法是先把文档拆成一句一句的，给每句算出一个向量，再比较相邻两句有多像。像，说明还在讲同一件事，继续放在一起；突然不像了，说明话题转了，就在那里切开。

比如这两句紧挨着：

一线城市每晚不超过 800 元，二线城市不超过 500 元。
员工出差应提前填写申请，经直属领导审批。

前一句在讲住宿标准，后一句已经转到审批流程，两句向量会拉开距离，语义切分就会在这里断。反过来，「超标部分由个人承担」跟住宿标准是同一件事，相似度高，就会留在同一段里。

语义切分只需要 Embedding 模型，不需要接大模型。 它全程只是算向量、比距离，没有一次生成调用。

语义切分的代价也不小。普通切分不需要额外调模型，语义切分却要给每句话都算一次向量，而句子数远多于片段数。另外阈值也很难调：太敏感，一段话会被切得过于细碎；太迟钝，又跟没切差不多。

我的建议是：先把递归切分 + 结构化切分做好，绝大多数场景够用了。语义切分留到文档结构很乱、靠标点和标题找不到话题边界时再上。

框架支持情况

上面这几种方法，两个主流框架（Spring AI 和 LangChain）的支持程度差得很远，后面会详细讲，这里稍微了解下。

LangChain：四种切分方式都有现成类。

切分器都在 langchain_text_splitters 包里：

  • 固定长度： CharacterTextSplitter （按单一分隔符切）、 TokenTextSplitter （直接按 token 数切）
  • 递归字符： RecursiveCharacterTextSplitter ，还有个 from_language() 工厂方法，内置了二十多种编程语言的分隔符（ Language.PYTHON 、 Language.JAVA ），切代码也不用自己配置分隔符。
  • 结构化： MarkdownHeaderTextSplitter 、 HTMLHeaderTextSplitter 、 HTMLSectionSplitter 、 RecursiveJsonSplitter
  • 语义： SemanticChunker

Spring AI：官方只支持固定长度切分。

Spring AI 支持有 TokenTextSplitter 。递归字符切分、结构化切分、语义切分都没有现成实现。Spring AI 的生态中，存在一些非官方的扩展实现。例如， spring-ai-alibaba 就提供了递归字符切分 RecursiveCharacterTextSplitter

四、Chunk 大小与重叠

Chunk 到底切多大合适？

chunk 越小，检索越准但上下文越不完整；chunk 越大，上下文越完整但检索越不准。

先说为什么大 chunk 检索不准。因为**一个片段只有一个向量。**片段里塞了五个话题，这个向量就是五个方向的平均值，跟其中任何一个具体问题都不够接近。用户问的是第三个话题，向量被另外四个话题拉离了目标方向。也就是说， 信息被稀释了。

这也解释了一个很多人觉得反直觉的现象：明明把 chunk 调大、让片段包含了更多信息，检索效果反而变差了。

那反过来，把 chunk 切得足够小，是不是就没问题了？

也不行，检索是准了，可检索到的片段模型读不懂。比如切出这么一段：

超出上述标准的部分由个人承担，特殊情况需提前报备。

「上述标准」是什么？被切走了。这段话单独看缺少必要信息，给到模型之后，模型只能猜，或者干脆答不出来。

中文文档里这个问题格外突出 ，因为中文习惯用「该」「上述」「前款」这类指代词。一旦前文被切掉，片段就缺少指代对象，语义不完整。前面反复强调的结构化切分和上下文增强，本质上都是在补救这件事。

Chunk太大也不行，太小也不行，所以，实际的做法是先挑一个合理的起点，再拿评测集往两边试。

chunk_size（字） 适合的场景
150 ~ 300 FAQ、条款、术语表
300 ~ 600 通用文档问答， 大多数项目从这里开始调整
600 ~ 1200 需要连贯推理的技术文档、分析报告
整节不切 结构清晰且小节本身不长的文档

再强调一遍： 这是起点，不是答案。 你需要用评测集去测评切分得是否合理，再决定往哪边调，直到效果你满意为止！

不过 chunk_size 只管片段有多长，管不了断点具体落在哪儿。哪怕你把 chunk_size 挑得很合适，也总会有一句关键的话，正好落在两个片段的接缝上。这次不是因为切太小，只是断点恰好落在关键句上。

overlap（重叠） 就是为解决这个问题发明的：让相邻片段共享一小段内容，前一段的尾巴同时出现在后一段的开头。这样接缝处的话，总能在其中一个片段里保持完整。举个例子，原文里有这么一段：

员工在一线城市出差，住宿费每晚不超过 800 元；在二线城市出差，住宿费每晚不超过 500 元。超出标准的部分由个人承担，特殊情况需提前报备。

如果没有 overlap，刚好切成两段，可能会变成这样：

片段 A：员工在一线城市出差，住宿费每晚不超过 800 元；在二线城市出差，住宿费每晚不超过 500 元。
片段 B：超出标准的部分由个人承担，特殊情况需提前报备。

用户问「住宿费超标怎么办」时，片段 B 很可能被检索出来，但模型只看到「超出标准」，不知道标准是多少，也不知道说的是住宿费。

加上 overlap 之后，片段 B 的开头会带上前一段的尾巴：

片段 B：在二线城市出差，住宿费每晚不超过 500 元。超出标准的部分由个人承担，特殊情况需提前报备。

这样模型至少能知道「超出标准」指的是住宿费标准，回答会准确得多。

overlap的经验值是 chunk_size 的 10%~20%。如果你用的是结构化切分，可以直接设 0，因为断点本身就落在语义边界上，接缝处不会有断句。

overlap 不宜设得过大。 我见过设成 50% 的，索引体积直接翻倍，检索出来的 Top-5 里三段内容高度重复，上下文窗口被重复内容占满。

讲到这里你可能会问：Chunk 大有大的问题、小有小的问题，就没有两全的办法吗？

有，用小片段做检索，命中之后把它所属的大片段取出来给模型。

检索走小片段，向量不被稀释，精度高；喂给模型的是大片段，上下文完整，指代关系也齐全。两个目标各自用最合适的粒度，不再互相牵制。

落地方式有三种，按实现成本从低到高：

  • 索引小片段，元数据里记 parent_id ，命中后按 parent_id 把父片段拉出来（LangChain 里对应 ParentDocumentRetriever ）
  • 索引小片段，元数据里记它在原文中的起止位置，命中后按位置往前后各扩若干字
  • 索引一句话摘要，正文原文存在元数据里，检索匹配摘要、返回原文

这套做法几乎没有副作用，代价只是索引结构复杂一点。 一旦你发现 chunk 参数怎么调都是「提高精度就会损失完整度，反之亦然」，就该上它了，而不是继续只调整 chunk_size。

五、数据更新与版本管理

前面几节默认文档处理完就入库，索引也就固定了。真实项目里文档不会不停变动：制度改版、旧文件作废、新文件进来，向量库里的索引得跟着改。这一节就讲索引建好之后，怎么跟上这些变化。

先说最常见的情况：更新。

库里有两千份文档，今天有人改了其中一份差旅制度。最省事的办法是两千份全部重跑一遍，但 Embedding 又贵又慢，为改一份重算两千份，显然不划算。正确的做法是 增量更新 ：只动真正变了的那些片段。

可你怎么知道哪些片段变了？给每个片段算一个 内容哈希 。同一段文本算出来的哈希相同，改了一个字，哈希就会变。拿这份文档新旧两批哈希对比，就能看出哪些是新加的、哪些删掉了、哪些没动。

关键在第 5 步： 没变的片段直接跳过，一次向量都不用重算。 对「文档只改了一个错别字」这种最常见的情况，一份文档里绝大多数片段的哈希都没变，这套逻辑能省下 99% 的开销。

更新讲完，接着说删除。

它看着最简单，却是最容易出事的。RAG 系统最常见的数据事故，就是文档删了，但向量还留在库里。

设想这样一个场景：一份报销制度作废了，管理员把文件删掉了，以为这事就结束了。可这份文件对应的向量仍留在库中。三个月后，有新员工问起报销标准，系统仍会检索并返回这份作废文件，给出了早已过期的答案。

这类 bug 极其隐蔽 ，因为答案看起来完全正常，格式、语气、引用一应俱全，你根本想不到它引的是一份早该消失的文件。

要解决这个问题，我们得做好三件事。

第一， 每个片段都带上 doc_id ，这样删文档时才能按 doc_id 把它的全部片段一次精确清掉。

第二， 优先用软删除，而不是直接做物理删除。 给片段打一个 deleted=true 的标记，检索时把带标记的过滤掉，数据本身仍保留。这样万一删错了还能找回来。

第三， 定期跑一致性校验。 拿向量库里的 doc_id 集合，和源系统里现存的文档对一遍，把两边对不上的数据找出来。这是兜底的最后一道防线。

不过，删除也不总是「越干净越好」。制度类文档就有个相反的需求： 旧版本不能真扔掉。 因为有人会问「去年的报销标准是多少」，真出了纠纷，也得能追溯当时依据的是哪一版。

处理办法我们在元数据那一节其实已经提到过：把版本号和生效期存进元数据，检索时默认只查现行版本，需要追溯历史时，再放开过滤条件去查旧版本。

最后要交代的是，有两种情况，增量这套逻辑会彻底失效， 必须整库全量重建 。

一种是 换了 Embedding 模型。 比如你从 OpenAI 的 text-embedding-3-large 换成了国产的 Qwen3-Embedding 。不同模型的向量空间是完全不通的两套坐标系，新旧向量混在一个库里算相似度，结果基本等于随机。下一篇还会再专门强调。

另一种是 改了切分策略。 只要你动了 chunk 大小、overlap 或者分隔符，片段边界就全变了，哈希自然对不上，增量的差集算出来会是「全删全增」，等于变相全量重建，还不如直接做全量重建来得干净。

正因为「全量重建」这件事早晚都会碰上，工程上有个强烈建议： 把索引构建做成一条能一键重跑的流水线，并且支持双索引切换。

所谓双索引切换，其实就是软件部署里蓝绿发布的思路：新索引在旁路先建好，用评测集验证通过之后，再把线上流量切过去；万一新索引有问题，随时能切回旧的。这样重建的过程用户完全无感，还自带回滚能力。
