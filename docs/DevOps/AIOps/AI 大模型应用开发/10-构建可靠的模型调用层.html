10-构建可靠的模型调用层

前面几篇已经把「怎么调模型」讲完了。发出请求、拿到回复，在本地写一段示例代码，这些都够用。

放到生产环境里，情况就不一样了。模型服务在远端，一次调用常常要跑好几秒。网络会抖动，厂商会限流，服务端会偶发 500，某个区域还会整体不可用。

这一篇我们要在业务代码和模型服务之间，加一层专门负责调用的代码，也就是 调用层 。业务代码只管「这次要问什么」，超时、重试、限流、降级，都交给这一层统一处理。

一、统一调用层

我们先来看一个典型的反例。项目里通常不止一处要调大模型。客服模块里写一行 client.chat.completions.create(...) ，摘要模块里再写一行，标签模块里再写一行。本地跑起来没问题，一时也看不出有什么隐患。

等到你要改调用方式，问题就来了。给请求加超时，每个调用的地方都得改一遍。厂商限流了，要加上重试，还是每个地方改一遍。想从通义千问切到 DeepSeek 做成本对比，同样要把所有调用点找出来改掉。

这些地方往往还不是同一个人写的：有的加了 try ，有的没有；有的重试三次，有的重试十次。超时设多少、失败要不要重试，项目里其实没有一个统一的规定，只是各写各的。

所以调用层必须做成全项目共用的一处，把所有调用收口到这里。它放在业务代码和模型服务中间：超时、重试、限流、降级、日志、成本统计都在这一层处理，业务模块只需要调用一个函数，把「要问什么」传进去。

有了统一调用层之后，以后要改超时、加重试、换模型，只改这一层。下面几节就按超时、重试、限流、降级这个顺序，把这些能力一项项加进统一调用层。

二、超时设置

往调用层里加的第一项，是超时（Timeout）。

大模型生成本来就慢，一次请求花几秒到几十秒很正常。如果网络抖动，或者服务端卡住了，而你又没有设超时，这个请求就会一直挂着。

挂着的请求会占住一个线程。请求一多，线程池被占满，整个服务对外就像全部卡死。一个慢接口把整个应用拖垮，这是线上很常见的一类事故。

超时并不是模型的参数，而是 HTTP 客户端的配置。OpenAI、Anthropic 这些官方 SDK 底层都带着一个 HTTP 客户端，Python 里通常是 httpx 。你在 SDK 里传的 timeout ，最后就是交给这个HTTP客户端去执行。所以要弄清楚超时，得先看 HTTP 客户端把一次请求拆成了哪几段。

以 httpx 为例，它不是只设「一个总超时」，而是按阶段分别计时。跟调用大模型最相关的是这两段：

  • 连接超时（Connect Timeout） ：建立 TCP 连接最多等多久。这个应该短，几秒就够。连不上，说明网络或服务不可用，应该尽快失败。
  • 读取超时（Read Timeout） ：等待下一块数据到来的最长时间，也就是两次收到数据之间的最大间隔。每收到一点数据，这个计时器就清零重来。它不是「整个请求的总时长」，这一点最容易理解错。

正因为读取超时看的是「块与块之间的间隔」，流式和非流式要分开设。

非流式调用里，服务端会等整段内容全部生成完，才一次性把响应体发回来。模型在那几十秒里持续生成的时候，你这边一个字节都收不到，读取计时器会一直走。所以非流式的读取超时必须足够大，要能覆盖最坏情况下一次完整生成要多久，比如 60 秒甚至更长。设短了，一段正常的长回答也会被当成超时打断。

流式调用则相反。数据是一个 Token 一个 Token 往回推的，正常情况下每隔几十到上百毫秒就有新数据到，读取计时器会频繁清零，根本不会触发超时。这时候读取超时的作用，是检测流是不是卡住了：只有当很长时间没有任何新数据，比如服务端卡死、连接假死，才会触发。所以流式的读取超时可以设得比非流式小，比如 15 到 30 秒。这样能把真的卡住的请求断掉，又不会把一段正在正常输出、只是内容比较长的流误判成超时。

还有一个常见问题：流式有没有「总超时」？ httpx 这类客户端本身不提供对整条流的总时长限制，它只管上面说的块间间隔。这样是合理的，因为一条健康的流本来就可能持续输出好几分钟。

如果你的业务确实需要给一整次流式调用加上总时长上限，比如最长不超过 5 分钟，那就得自己在代码里做，不能指望读取超时。常见做法是记下开始时间，在 for chunk in stream 的循环里检查有没有超过截止时间，或者用 asyncio.wait_for 给整个流式过程包一层 deadline。

import httpx

# 超时是 HTTP 客户端的配置，SDK 只是把它透传下去。
# 注意：read 不是"总超时"，而是"两块数据之间的最长间隔"。
# - 非流式：生成期间一直收不到数据，read 要覆盖最坏的完整生成耗时
# - 流式：数据持续到达，read 只用来检测"流卡死"，可以设小一些
timeout = httpx.Timeout(connect=5.0, read=60.0, write=10.0, pool=5.0)

# 若还想给"一整次流式调用"加总时长上限，HTTP 客户端不管这事，得自己实现：
import time
deadline = time.time() + 300          # 整条流最长 5 分钟
for chunk in stream:
    if time.time() > deadline:
        raise TimeoutError("流式总时长超限")   # 主动中断
    ...  # 正常处理 chunk

三、重试

超时能把挂死的请求断掉，但断掉之后，这次调用还是失败了。限流、偶发 500、网络抖动这类问题，再发一次往往就能恢复，所以调用层还要会重试。

这里说的重试，发生在「应用服务器 → 大模型服务」这一段。调用层发现发给模型的那次 HTTP 请求失败了，就自动再发一次。它和「前端 → 应用服务器」无关，前端不用知道底下重试了几次，只等最终结果就行。

重试之前，先要分清这个错误该不该重。不问原因、失败了立刻反复重发，只会把故障放大，多花一笔调用费用。服务端如果本来在恢复，过量重试还可能把它再次压垮。

一类是 可重试的错误 ，共同特征是重发一次很可能就好了：

  • 429 Too Many Requests ：触发了限流，稍等再试大概率能成功。
  • 5xx 服务端错误（500 / 502 / 503）：服务端临时异常。
  • 网络层错误：连接超时、读取超时、连接被重置。

另一类是 不可重试的错误 ，重发多少次都不会好：

  • 4xx 客户端错误（429 除外）：比如 400 参数写错了、 401 鉴权没过、 404 模型名不存在。这些是请求本身的问题，重试只会浪费时间和费用。

该重试的错误，失败后也不要立刻重发。正确做法是 指数退避加抖动 ，并且设一个重试上限。

指数退避 是指每次重试的等待时间成倍增长，比如 1 秒、2 秒、4 秒，给服务端留出恢复时间。 抖动 是在这段等待时间上再加一个随机量，避免大批客户端在同一时刻一起重试，形成 重试风暴 ，把刚恢复的服务端再次压垮。

重试次数也要有上限，一般 2 到 3 次就够。超过就停止，把失败返回给业务代码。

底层的 HTTP 客户端，默认几乎不会替你重试业务错误。 httpx 的 retries 只在连接还没建立起来时才生效，对 429、500 这类已经连上、但服务端返回了错误的请求根本不会重试。 requests 底下的 urllib3 可以配一个 Retry 对象按状态码重试，但也要你自己打开。

官方 SDK 就不一样了。OpenAI、Anthropic 这些 SDK 大多自带重试，默认就会对 429、5xx、网络错误自动重试 2 次，并且带了指数退避。次数用 max_retries 就能改：

# 示意代码，接口以官方文档为准
from openai import OpenAI

# SDK 层自带重试：这里配成最多重试 3 次
client = OpenAI(max_retries=3)

日常场景用 SDK 自带的这套就够。只有 SDK 做不到你要的事情时，才值得在调用层里再包一层。

四、限流

在生产里，你遇到的 429 有一大半根本不是服务端异常，而是你自己 调用过于频繁，触达了厂商的限流（Rate Limiting） 。

厂商为什么要限流？很简单：GPU 是稀缺资源，它得在所有客户之间公平分配，不能让某一个客户端独占全部算力。所以每家都会给你的账号设配额上限。 不同厂商的限流方式差别很大，绝不能拿一套参数套所有平台。

笼统地，我们可以把限流方式分为三类。

第一种，按「每分钟」限，也是最主流的一种：RPM + TPM 双维度。 「RPM」是每分钟请求数（Requests Per Minute），「TPM」是每分钟 Token 数（Tokens Per Minute，输入输出都算）。这俩是「或」的关系， 任意一个超了就触发 429 。

国内的 通义千问（Qwen） 就是典型：在阿里云百炼平台上， qwen3.8-max 这类主力模型的额度约为 RPM 30000、TPM 500 万，而且限流是 按主账号 + 模型 统一算的，你名下所有 API Key、所有业务的调用量是合并计数、共享这一份额度的。

第二种，完全不按「每分钟」限，而是按「并发数」限。 这是 DeepSeek 官方 API 的做法。

DeepSeek 不看你一分钟发了多少个请求，只看你 同一时刻有多少个并发请求 （从请求发出到响应完成，算占用一个并发连接）。它给的额度大致是： deepseek-v4-pro 500 并发、 deepseek-v4-flash 2500 并发，同样是 账号级共享 ，超了返回 429。

这个差异直接决定了限流器怎么写：对 Qwen 你要控「每分钟的速率」，对 DeepSeek 你要控「在途请求的数量」，前者用令牌桶，后者用信号量（Semaphore）。

第三种，按「账号等级」阶梯放开：用量分层（Usage Tier）。 国外的 OpenAI、Anthropic（ claude-sonnet-5 ） 走的是这条路：账号按累计消费划成 Tier 1 到 Tier 5，等级越高，每个模型的 RPM/TPM 上限越大。新号一开始额度很小，很容易一测试就触达上限，得靠持续消费或预充值提升等级，额度才会随之提高。

看懂了这三种限流方式，应对策略其实是共通的，核心就八个字： 主动限速 + 被动退避 。

主动限速 ：别等返回了 429 再说，而是在调用层里放一个限速器，把请求速率主动压在额度以内，从源头减少 429。用哪种限速器，取决于上面是哪种限流方式。按 RPM/TPM 限的（如 Qwen）用 令牌桶（Token Bucket） 控制速率，按并发限的（如 DeepSeek）用 信号量 卡在途数量。高并发场景下，还可以在前面加一个 排队（Queue） ：请求先入队，由固定速率的消费者匀速发出，既不超限，又能削峰填谷。

被动退避 ：主动限速只能压低429的概率，真返回了 429 还得退避重试（就是第三节那套指数退避）。但这里有个很多人漏掉的关键细节： 优先读响应头里的 Retry-After 。厂商往往会明明白白告诉你「再等 N 秒再重试」，直接按它给的时间等，远比自行估算的退避时间精准。

最后补一个降本增效技巧：如果任务不赶时间（离线打标、批量总结），优先走 批处理（Batch）接口 。像 Qwen 用 Batch API 提交的任务 完全不占 RPM/TPM 限流额度 ，价格通常还更便宜。用它跑批量任务，等于避开了限流限制。

五、模型路由与故障降级

厂商机房会宕机、某个区域会网络中断、某个模型版本会被临时下线，你把重试、退避写得再漂亮也没用。

这时候需要的是另一套思路： 模型路由（Model Routing）与故障降级（Fallback / Graceful Degradation） ，核心是不要只依赖单一厂商或单一模型。

先说 模型路由 ，它其实是把「选哪个模型」这件事从业务代码里收进调用层，按请求的实际需要动态分配。

最实用的一条原则是 按任务难度选模型，别动辄就上最贵的 ：一个「判断评论是好评还是差评」的简单分类，用便宜快速的小模型（比如 gpt-5.6-luna 、 deepseek-v4-flash ）几毫秒即可完成，非要调 gpt-5.6 这种旗舰版本属于过度配置、成本过高；只有真正需要复杂推理、长文写作的请求，才把它路由到强模型上。

再说 故障降级 ，通常分两级：

  • 主备模型 ：给关键链路配一个备用模型，而且 强烈建议来自不同厂商 。因为同一家厂商往往一挂就是全挂，你拿 gpt-5.6 做备用 gpt-5.6-luna ，OpenAI 一旦区域故障，两者会一起不可用，等于没有备用。正确做法是主用 gpt-5.6 、备用切到国产的 qwen3.8-max 或 deepseek-v4-flash ，一家出事立刻换另一家，从根上避免单点故障。
  • 兜底响应 ：万一主备都失败，也不能只给用户返回一个 500 页面。这时返回一个预设的兜底话术（「服务繁忙，请稍后再试」）、走规则引擎的简单应答，或者干脆返回缓存里的历史答案，核心是 保证链路不断、用户体验仍可接受 。

六、统一调用接口

上一节说，主模型和备用模型最好来自不同厂商。可各家的调用方式并不一样，业务代码如果直接调某一家的原生接口，切换备用时就得把调用代码重写一遍。

OpenAI 用 chat.completions ，消息放在 messages 里；Anthropic 的 Claude 虽然也叫 messages 接口，但系统提示要单独作为字段传入，返回结构也不一样；国产平台又各有各的 SDK 和字段。

业务代码一旦按其中一家来写，就和这家绑在一起了。以后要加备用厂商，或者整体迁到另一家，调用代码就得重写。

所以调用层还要再做一件事：对上只暴露一套与厂商无关的接口，比如 chat(messages, model) ；对下由内部的 适配器 ，把这套统一格式翻译成各家的原生请求，再把各家的原生响应翻译回统一的结果。这样，换厂商、加备用，就变成多写一个适配器，业务代码不用改。

实际做的时候，适配工作往往没有想象中那么多。OpenAI 的 API 格式已经是行业里最常见的写法，DeepSeek、Qwen、GLM、Kimi 等国产平台大多提供了「OpenAI 兼容模式」。很多时候你不用自己写适配器，直接用官方 OpenAI SDK，改一下 base_url 、 api_key 和模型名就行。

# 示意代码，接口以官方文档为准
from openai import OpenAI

# 还是那套 OpenAI SDK，仅靠改 base_url 就切到了国产厂商
client = OpenAI(base_url="https://api.deepseek.com", api_key="...")
resp = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[{"role": "user", "content": "你好"}],
)

这能省掉一大半适配工作，但这通常只覆盖最基础的对话补全。一旦用到工具调用（Function Calling）、结构化输出、思考过程（ reasoning_content ）、多模态这些能力，各家的字段和用法又不一样了。走兼容接口无法使用这些特性。所以「统一按 OpenAI 的写法来接」能少写很多适配代码，却不能让适配层完全消失。

七、可观测性

线上的模型调用本质是个黑盒，你发出去、它给你回来，中间快了慢了、贵了省了，如果不主动记录，出了问题你就只能靠猜。所以必须主动采集指标和日志。这就是 可观测性（Observability） 。

具体来说，有三样东西每次调用都必须记录：

Token 用量（usage） ：每次调用都记下 prompt_tokens （输入）和 completion_tokens （输出）。不记的话，月底账单一来，你根本搞不清这几千块钱到底是客服模块消耗的、还是那个批量总结任务消耗的，更没法按模型、按业务去优化。

延迟（Latency） ：这里有个新手最爱踩的坑： 只看平均值 。你真正要看的是 分位数 P50 / P95 / P99 （意思是 50% / 95% / 99% 的请求都比这个值快）。很可能平均值 2 秒，P99 却已经达到 30 秒。这意味着有 1% 的请求延迟达到了半分钟。

另外，流式场景下还要特别关注一个指标： 首 Token 延迟（TTFT，Time To First Token） ，它直接决定了用户「点下发送后，等了多久才看到第一个字出现」，是流式体验优化的关键。

调用日志记录 ：每次调用还要记下这次用的哪个模型、重试了几次、有没有触发降级、最终是成功还是哪一类失败。有了这些，你才能回答「最近降级频率是不是变高了」「 gpt-5.6 是不是最近特别容易超时」这类问题。
