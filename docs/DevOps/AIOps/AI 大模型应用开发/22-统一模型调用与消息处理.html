22-统一模型调用与消息处理

上一篇讲了框架的价值。这一篇我们把模块二写过的调用、消息、多轮对话、模板、流式，用框架重写一遍。

另外需要说明，本篇涉及的版本是 Spring AI 2.0.x 和 LangChain 1.x（Python） 。这两个框架都做过破坏性升级，网上大量教程还停留在旧版本，写法不一致的情况很常见。开始编写之前，先确认自己的版本。

一、先把它跑起来

从最小可运行的例子开始，Spring AI 和 LangChain 各写一份。

Spring AI。 先引 BOM 统一管版本，再引如模型的 starter：

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.ai</groupId>
      <artifactId>spring-ai-bom</artifactId>
      <version>2.0.1</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai</artifactId>
  </dependency>
</dependencies>

配置写在 application.yml 里：

spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
      chat:
        options:
          model: gpt-5.6
          temperature: 0.7

然后注入 ChatClient.Builder 就能用了：

@RestController
class ChatController {

    private final ChatClient chatClient;

    // 自动配置会准备好 ChatClient.Builder，直接注入即可
    ChatController(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    @GetMapping("/ask")
    String ask(@RequestParam String q) {
        return chatClient.prompt()
                .user(q)
                .call()
                .content();
    }
}

LangChain ：

pip install -U "langchain[openai]"    # 注意 LangChain 1.x 要求 Python 3.10 以上

from langchain.chat_models import init_chat_model

# init_chat_model 会自己去环境变量读 OPENAI_API_KEY
model = init_chat_model("gpt-5.6", temperature=0.7)

print(model.invoke("出差住酒店最多能报多少钱？").text)

两边都只有几行，框架帮我们做了很多工作：读环境变量、构造 HTTP 客户端、拼鉴权头、设默认超时、解析响应 JSON、失败重试。这些你在模块二里都是自己写的，现在都由框架完成。

如果我们想换成其他模型，前面讲过，DeepSeek、Qwen、GLM、Kimi 等大多都提供了 OpenAI 兼容接口，所以不用换 SDK，只需修改地址：

# Spring AI：还是 openai 这套 starter，只换 base-url
spring:
  ai:
    openai:
      base-url: https://api.deepseek.com
      api-key: ${DEEPSEEK_API_KEY}
      chat:
        options:
          model: deepseek-v4-flash

# LangChain：同理，走 openai provider + base_url
model = init_chat_model(
    model="deepseek-v4-flash",
    model_provider="openai",
    base_url="https://api.deepseek.com",
    api_key=os.environ["DEEPSEEK_API_KEY"],
)

这里出现了一个后面会反复用到的词： provider（模型提供方） 。它指的是框架为某一家厂商写的那套对接实现，负责拼这家的请求格式、解析这家的响应格式。在 LangChain 里，provider 由 model_provider 参数指定；在 Spring AI 里，一个 provider 就对应一个 starter 模块，比如 spring-ai-starter-model-openai 。

理解了这个词，上面两段配置就更容易看懂了： 模型换成了 DeepSeek，但走的仍然是 OpenAI 这个 provider 。之所以能这样，正是因为 DeepSeek 提供了 OpenAI 兼容接口，请求和响应格式对得上。

二、消息Message

模块二讲过，一次对话就是一个消息列表，每条消息有角色。框架为每种消息定义了不同的类。

角色 Spring AI LangChain
系统消息 SystemMessage SystemMessage
用户消息 UserMessage HumanMessage
模型回复 AssistantMessage AIMessage
工具结果（Agent开发中使用） ToolResponseMessage ToolMessage

LangChain示例：

from langchain.messages import SystemMessage, HumanMessage, AIMessage

conversation = [
    SystemMessage("你是公司的差旅制度助手，只依据制度原文回答。"),
    HumanMessage("出差住酒店最多能报多少钱？"),
    AIMessage("一线城市每晚不超过 800 元。"),
    HumanMessage("那二线城市呢？"),
]
response = model.invoke(conversation)

Spring AI 示例：

List<Message> messages = List.of(
        new SystemMessage("你是公司的差旅制度助手，只依据制度原文回答。"),
        new UserMessage("出差住酒店最多能报多少钱？"),
        new AssistantMessage("一线城市每晚不超过 800 元。"),
        new UserMessage("那二线城市呢？"));

String answer = chatClient.prompt()
        .messages(messages)
        .call()
        .content();

上面这个 messages 列表，是你自己保存并组装起来的。模块一讲过 API 是无状态的，这一点用了框架也不会变。框架确实提供了记忆能力，但那是另外一套组件，必须显式开启，下一篇会专门讲它。

三、模型回复

上一节的消息类型结构清晰，但它建立在一个前提上： 模型的回复就是一段文字 。这个前提，这两年已经不成立了。

我们举个例子来解释。假设我们要把差旅助手换成推理模型，产品经理提了三个要求：

  1. 思考过程折叠在「已深度思考」里，用户点开可以查看；
  2. 正文仍然逐字输出；
  3. 助手查询制度库的时候，界面上显示「正在检索」的加载状态。

这三个要求对应三种内容： 思考、正文、工具调用 。它们包含在同一次回复中返回，需要你把它们区分开。

区分这三类内容并不复杂，但各家厂商的原始响应结构并不一致。

DeepSeek 是在消息上增加一个平级字段：

{"role": "assistant",
 "reasoning_content": "用户问的是二线城市……",
 "content": "二线城市每晚不超过 500 元。"}

Anthropic 是一个数组，每项自带 type ：

{"role": "assistant", "content": [
  {"type": "thinking", "thinking": "用户问的是二线城市……", "signature": "..."},
  {"type": "text", "text": "二线城市每晚不超过 500 元。"}
]}

OpenAI 的 Responses API 又是另一种结构，思考是 output 数组里一个独立条目，而且只返回摘要，不返回原文：

{"output": [
  {"type": "reasoning", "summary": [{"type": "summary_text", "text": "正在核对二线城市标准……"}]},
  {"type": "message", "content": [{"type": "output_text", "text": "二线城市每晚不超过 500 元。"}]}
]}

同样一次回复，DeepSeek 用平级字段，Anthropic 用带 type 的数组，OpenAI 用另一种带 type 的数组。 按 DeepSeek 的结构写出来的解析代码，换到 Anthropic 需要完全重写。

两个框架给出了两种不同的解决方式。

LangChain 的做法：统一成内容块

LangChain 1.0 定义了一套 标准内容块（content blocks） 。它的思路是，无论底层厂商把思考过程叫 reasoning_content 还是 thinking ，进入 LangChain 之后一律转换成 {"type": "reasoning", ...} ，正文一律转换成 {"type": "text", ...} 。

回到前面的三个要求，用内容块实现出来就是几个分支判断：

for chunk in model.stream("那二线城市呢？"):
    for block in chunk.content_blocks:
        if block["type"] == "reasoning":
            print("[思考]", block.get("reasoning"))     # 对应折叠区
        elif block["type"] == "text":
            print(block["text"], end="")                # 对应正文，逐字输出
        elif block["type"] == "tool_call_chunk":
            print("[正在检索]", block)                   # 对应加载状态

这段代码换成 Anthropic 或 OpenAI 都不需要修改。 这就是这层抽象带来的收益。

Spring AI 的做法：为每类内容定义固定字段

Spring AI 没有内容块这一层，它为 每一类内容定义一个固定字段 。同样是取出思考、正文和工具调用，代码是这样的：

ChatResponse response = chatClient.prompt().user("那二线城市呢？").call().chatResponse();
AssistantMessage message = response.getResult().getOutput();

String text = message.getText();                            // 正文
List<AssistantMessage.ToolCall> toolCalls = message.getToolCalls();  // 工具调用
List<Media> media = message.getMedia();                     // 图片、音频

// 思考过程没有对应字段，从Map<String, Object> metaData专门放那些没有正式字段可放的附加信息中获取。
String reasoning = (String) message.getMetadata().get("reasoningContent");

前三行都是直接读字段： getText() 取正文， getToolCalls() 取工具调用， getMedia() 取图片音频。到 Spring AI 2.0 为止， AssistantMessage 上仍然没有承载思考过程的标准字段，只能从 Message 上的一个专门放那些没有正式字段可放的附加信息中获取。

四、提示词模板

关于提示词模板，我们在模块三的第3篇文章中已经讲解了，当时还提到了Spring AI 和 LangChain中的提示词模板。这里再回顾一下。

Spring AI 默认用 StringTemplate 引擎，变量写成 {变量名} ：

String answer = chatClient.prompt()
        .system(s -> s.text("你是一名{role}，回答要简洁。").param("role", "差旅制度专家"))
        .user(u -> u.text("请回答：{question}").param("question", question))
        .call()
        .content();

LangChain 用 ChatPromptTemplate ，默认是 Python 的 f-string 风格：

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是一名{role}，回答要简洁。"),
    ("human", "请回答：{question}"),
])

messages = prompt.invoke({"role": "差旅制度专家", "question": question})
response = model.invoke(messages)

需要注意的是，提示词里放 JSON 示例，会和模板变量语法冲突。

这个问题非常常见，因为模块三教过「给模型一个输出格式示例」是提高稳定性的有效手段，而 JSON 示例里全是花括号。模板引擎会把 { 解析成变量起始符，轻则渲染出错误的内容，重则直接抛出「变量未提供」的异常。

Spring AI 的解决办法是换分隔符：

String answer = chatClient.prompt()
        .user(u -> u.text("按这个格式输出：{\"name\": \"...\"}，主题是 <topic>")
                    .param("topic", topic))
        // 把变量分隔符从 {} 换成 <>，就不会和 JSON 的花括号冲突了
        .templateRenderer(StTemplateRenderer.builder()
                .startDelimiterToken('<')
                .endDelimiterToken('>')
                .build())
        .call()
        .content();

这是官方文档给出的写法，但尖括号在实际项目里未必合适。写提示词时有一种很常见的做法，是用 <document> 、 <example> 这类标签把不同部分隔开。一旦把分隔符设成 < 和 > ，模板引擎就会把 <document> 当成变量，同样会抛出「变量未提供」的异常。结果是不再和 JSON 的花括号冲突，却又和标签的尖括号冲突了。

那能不能像 LangChain 那样用 {{topic}} 这种双花括号？ StTemplateRenderer 做不到。它的 startDelimiterToken() 和 endDelimiterToken() 接收的参数类型是 char ，只能传单个字符，底层的 StringTemplate 引擎本身就是这么设计的。

如果要用双花括号，就得自己实现 TemplateRenderer 接口。这个接口只有一个方法，实现起来并不复杂：

class MustacheTemplateRenderer implements TemplateRenderer {

    // 仅匹配双花括号，单个花括号一律当作普通文本
    private static final Pattern VARIABLE = Pattern.compile("\\{\\{\\s*(\\w+)\\s*}}");

    @Override
    public String apply(String template, Map<String, ?> variables) {
        Matcher matcher = VARIABLE.matcher(template);
        StringBuilder rendered = new StringBuilder();
        while (matcher.find()) {
            String name = matcher.group(1);
            if (!variables.containsKey(name)) {
                throw new IllegalStateException("模板变量未提供：" + name);
            }
            String value = String.valueOf(variables.get(name));
            matcher.appendReplacement(rendered, Matcher.quoteReplacement(value));
        }
        matcher.appendTail(rendered);
        return rendered.toString();
    }
}

用法和内置渲染器一样，传给 .templateRenderer() 即可：

String answer = chatClient.prompt()
        .user(u -> u.text("按这个格式输出：{\"name\": \"...\"}，主题是 {{topic}}")
                    .param("topic", topic))
        .templateRenderer(new MustacheTemplateRenderer())
        .call()
        .content();

这样 JSON 示例里的单花括号和提示词里的 XML 风格标签都不会被误解析。代价是放弃了 SpringAI 默认使用的 StringTemplate 模版引擎，也就放弃了对条件判断、循环、列表等复杂语法的支持，不过写提示词模板通常也用不到。

LangChain 的解决办法是将默认的模版引擎（f-string）改为mustache或者jinja2模版引擎。

prompt = ChatPromptTemplate.from_messages(
    [("human", "按这个格式输出：{\"name\": \"...\"}，主题是 {{topic}}")],
    template_format="jinja2",
)

LangChain 的三种模版引擎对比如下：

template_format 占位符写法 条件与循环 额外依赖
f-string （默认） {topic} 不支持 无
mustache {{topic}} 支持（section 语法） 无，LangChain 内置实现
jinja2 {{ topic }} 、 {% if %} 、 {% for %} 完整支持 需要 pip install jinja2

f-string 只做变量替换，不支持任何逻辑。另外提示词里出现 JSON 示例时，花括号必须写成 {{ }} 转义。

mustache 支持简单的语法，占位符默认为 {{}} 。它的好处是不用装额外的包。单个花括号不参与语法，JSON 示例可以原样写进提示词。

jinja2 支持复杂语法，条件、循环、过滤器、include、宏、模板继承都有，是三者里能力最完整的。

五、同步调用和流式调用

模块二第 5 篇讲过同步（也就是非流式）和流式调用。Spring AI 和 LangChain 两个框架都有支持。

Spring AI 用 call() 和 stream() 区分同步与流式：

// 同步
String text = chatClient.prompt().user(q).call().content();

// 要拿元数据（Token 用量、结束原因）就取 chatResponse
ChatResponse resp = chatClient.prompt().user(q).call().chatResponse();
Usage usage = resp.getMetadata().getUsage();

// 流式，返回 Reactor 的 Flux
Flux<String> stream = chatClient.prompt().user(q).stream().content();

// 消费方式一：订阅，每来一个分块就处理一次（异步，不阻塞当前线程）
stream.subscribe(chunk -> System.out.print(chunk));

// 消费方式二：拼成完整字符串（会阻塞，只适合测试或离线任务）
String full = stream.collect(Collectors.joining()).block();

LangChain 的实现同步和流式的方法如下：

# 同步
resp = model.invoke("出差住酒店最多能报多少钱？")

# 流式
for chunk in model.stream("写一段 200 字的差旅制度摘要"):
    print(chunk.text, end="", flush=True)

LangChain 的流式还有一个很实用的设计： 分块可以直接相加，聚合成一条完整消息。

full = None
for chunk in model.stream("解释一下什么是 Token"):
    full = chunk if full is None else full + chunk
# 循环结束后，full 就是一条完整的 AIMessage，可以直接追加进对话历史

六、框架对可靠性的支持

模块二最后一篇，我们讲述了如何设计一个可靠的大模型调用层：超时、重试、限流、降级、统计等。现在逐项对照一下，看看框架替我们做了多少。

能力 Spring AI LangChain
超时 各模型的 HTTP 客户端配置 初始化时传 timeout
重试 内置， spring.ai.retry.* 配置， max-attempts 默认 10 内置， max_retries 默认 6 次，指数退避带抖动
限流 无内置，用 Resilience4j 内置 InMemoryRateLimiter （仅按请求数限速）
降级 / 主备 无内置，用 Resilience4j .with_fallbacks([...])
Token 与延迟统计 内置 Micrometer 埋点 AIMessage.usage_metadata 、 get_usage_metadata_callback()
链路追踪 Micrometer Tracing LangSmith

这里有几处需要说明一下。

重试的默认值差别很大，而且次数都明显偏多。 LangChain 默认重试 6 次，Spring AI 的 spring.ai.retry.max-attempts 默认是 10 次。两边都对 429、5xx 和网络错误自动退避，对 401、404 这类不重试，判断逻辑跟模块二讲的完全一致。

但模块二说过「一般 2~3 次就够，超过这个次数就直接返回失败」。框架给的默认值明显大得多，一次失败的请求可能在后台连续退避十轮，而用户看到的就是界面一直在加载。 因此，这个值应该按你的超时预算调小。

限流的能力都很有限。 LangChain 的 InMemoryRateLimiter 只能按「每秒请求数」限制，无法限制 TPM，而且只在单个进程内生效，多实例部署时就失去了作用。模块二讲过 Qwen 按 RPM/TPM、DeepSeek 按并发数，计量口径完全不同。 这部分能力两个框架都没有覆盖，真正要控制住调用量，仍然需要自己引入分布式限流。

Spring AI 不直接提供降级和限流 ，因为 Spring 生态里 Resilience4j 已经是标准方案，重复实现没有意义。它只做「AI 特有」的那部分，通用的工程能力交给Spring 已有生态。

可观测性上 Spring AI 占优。 只要用的是自动配置的 ChatClient ，Micrometer 的指标和链路追踪就是默认可用的，不需要额外开发，接入现有的 Prometheus 和 Grafana 就能查看。这对企业应用来说确实省了不少工作。
