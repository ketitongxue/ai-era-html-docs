06-消息角色与多轮对话

上一篇我们留了个问题没回答： messages 为什么是个数组，而不是一段字符串？

毕竟在那个最小调用里，数组里只有一条消息，却仍要标注 "role": "user" 。只有用户发言时，这个身份字段看起来也是多余的。

答案在你再往下做一步的时候才会显现。你想把那段代码改造成一个能连续聊天的助手，只把用户的当前问题发过去，是不行的。第一轮你告诉它"我的项目用的是 Java 17"，模型给出简短回复；第二轮你问"那该选哪个 Spring Boot 版本"，它完全想不起来你说过 Java 17。

messages 数组就是模型能看到的全部世界。 它自己不存任何东西，你这次给它什么，它就只知道什么。所以这个数组必须能装下多条消息，不然上一轮的内容没地方放；也必须标清楚每条是谁说的，不然模型分不出哪句是你问的、哪句是它自己上轮答的。

这一篇我们就把 messages 这个数组讲清楚：三种角色分别管什么、多轮对话到底怎么"记住"上文等等。

一、三种消息角色：System、User、Assistant

messages 数组不是一组普通字符串，而是一个个带"身份"的对象，每个对象有 role （角色）和 content （内容）两个字段。角色只有三种，各司其职。

  • 系统提示词（System） ：给模型设定"人设"和规则的地方。你是谁、说话什么风格、能做什么不能做什么、输出格式要求，都写在这里。它在整段对话里持续生效。
  • 用户消息（User） ：用户说的话，也就是真正的问题或指令。
  • 助手消息（Assistant） ：模型自己的回复，你把它原样放回数组里。

一个最简单的多轮对话， messages 长这样：

messages = [
    {"role": "system", "content": "你是一个只用一句话回答的地理老师。"},
    {"role": "user", "content": "中国的首都是哪？"},
    {"role": "assistant", "content": "北京。"},
    {"role": "user", "content": "那它的人口大概多少？"},
]

模型看到最后那句"它的人口"，能正确理解"它"指北京，因为整个数组作为上下文一起发了过去。这就是多轮对话的核心机制，后面详细讲。

这里要纠正一个常见误解： 很多人把 System 当成"更高级、约束力更强"的指令，以为写在这里模型就一定照做，不是的。 System 只是优先级更高的一段文本，本质还是被拼进上下文、一并发给模型。你写"绝对不能透露你是 AI"，经过几轮诱导仍可能被绕过。System 是"强烈建议"，不是强制约束。真正的硬约束（比如不能返回某些内容）要靠你在应用层做后置校验，而不能只靠一句 System 就认为约束已经生效。

二、消息顺序与指令优先级

既然 System、User 都是文本，那它们冲突时听谁的？这就涉及优先级。

主流模型的大致优先级是： System > 靠后的消息 > 靠前的消息 。也就是说，System 整体权重最高；而在同类消息里，越靠近末尾的内容，模型越倾向于遵从，因为那是"最新的指令"，离它要生成的答案最近。

这带来两个非常实用的工程结论。

第一，把最重要的约束放 System，把当前这轮最具体的要求放在 User 消息末尾。 比如 System 规定"永远用 JSON 回答"，而某一轮用户临时说"这次用自然语言解释一下"，模型大概率会顺从后者。如果你不希望被覆盖，就得在 System 里把约束写得更明确、不允许例外，或者在应用层拦截。

第二，警惕"后文覆盖前文"带来的指令漂移。 对话很长时，早期 System 设定的风格会被后面几十轮的对话稀释、偏离原设定。比如，客服机器人聊到第 20 轮，突然不按规范话术说话了。原因往往就是早期 System 权重被大量后续内容冲淡。工程上的应对办法是：在关键轮次 重新注入或强调 System 指令 ，比如每隔若干轮，或在检测到偏离既定风格时，把核心规则再拼一遍到上下文靠后的位置。

三、无状态 API 与"记忆"的真相

现在讲最反直觉、也最重要的点。

你可能会觉得，我和模型聊了好几轮，服务器那边肯定存着我们的对话吧？ 恰恰相反。大模型的 API 是无状态的（Stateless）。每一次调用都是全新的、独立的、没有任何记忆的。 大模型不会帮你保存上一轮说了什么。这次请求结束，它不会保留任何上一轮状态。

那对话为什么能连续？因为 "记忆"是由应用（对话助手）自己构造的 。每次调用时，应用把你从头到现在的所有历史消息，重新放入 messages 数组一起发过去。模型看到的从来不是"第 5 轮"，而是"这 5 轮的完整文本"。它不是记得，它是每次都重新读了一遍全部历史对话。

理解了这点，很多现象就能解释清楚：为什么对话越长响应越慢、越贵（因为每次都在重发全部历史）；为什么同一个用户换个设备还能接着聊（因为历史存在应用的数据库里，不在模型那里）。

下面是一个实现"记忆"的示例代码：

from openai import OpenAI

client = OpenAI()

# history就是一个不断追加的数组，由你的应用维护
history = [
    {"role": "system", "content": "你是简洁的助手。"},
]

def chat(user_input: str) -> str:
    # 1. 把用户这轮的话追加进history
    history.append({"role": "user", "content": user_input})
    # 2. 把【完整历史】一起发出去——这就是"记忆"的来源
    resp = client.chat.completions.create(
        model="gpt-5.6",
        messages=history,
    )
    answer = resp.choices[0].message.content
    # 3. 关键：把模型的回复也追加回history，下一轮它才"记得"自己说过什么
    history.append({"role": "assistant", "content": answer})
    return answer

chat("我叫小王")
print(chat("我叫什么？"))  # 能答对，因为上一轮的信息被重发了

四、历史对话过长的应对策略

无状态机制有个严重副作用： 历史只会越来越长。 前面的章节中讲过上下文窗口（Context Window），即模型单次能处理的 Token 是有上限的。历史无限追加，迟早会超限报错；就算没超，成本也会明显上升。

这里要算一笔账，也是面试常被追问的点： 为什么对话成本不是线性的，而是接近平方级增长？

因为按 Token 计费，而你每一轮都要把前面所有历史重发。第 N 轮发送的 Token 约等于前 N-1 轮的累加。十几轮的闲聊成本差异还不明显，但客服、Agent 这类动辄几十上百轮的场景，Token 消耗会上升得很快。这就是为什么"管理历史"不是可选项，而是生产系统的必要工作。

常见的应对策略一般有两种，各有取舍。

策略一：滑动窗口，即只保留最近 N 轮。 最简单，实现只需要几行代码。缺点是"失忆"：用户开头说的关键信息（比如"我是 VIP 用户"）一旦滑出窗口就丢了。

def trim_by_turns(history, keep_rounds=6):
    system = [m for m in history if m["role"] == "system"]
    others = [m for m in history if m["role"] != "system"]
    # 一轮 = user + assistant 两条，保留最近 keep_rounds 轮
    kept = others[-keep_rounds * 2:]
    return system + kept

注意上面这个细节： System 消息必须单独取出并始终保留，不能被一起截掉。

策略二：摘要压缩（Summarization）。 当历史过长时，先调用一次模型，把早期对话压缩成一段简短摘要，用这段摘要替换掉那批原始消息。这样既省 Token，又保住了关键信息。代价是多一次模型调用，而且摘要可能丢细节。工程上常用"摘要 + 最近若干轮原文"的组合：远期用摘要，近期用原文。

拼出来的 messages 是这样的，注意摘要是数组里独立的一条，不要和其他内容写在同一个 content 里：

messages = [
    {"role": "system",    "content": "你是XX电商的客服助手，规则..."},   # 静态人设
    {"role": "system",    "content": "对话摘要：用户是VIP，咨询过退款，已确认订单号12345"},
    {"role": "user",      "content": "..."},        # 以下是最近 3 轮原文
    {"role": "assistant", "content": "..."},
    {"role": "user",      "content": "..."},
    {"role": "assistant", "content": "..."},
    {"role": "user",      "content": "本轮问题"},
]

摘要的角色为什么是 System 而不是 User？因为它是 应用注入的状态，不是任何一方真说过的话 。放 System 语义最准，优先级也高，不容易被后面的对话稀释；要是当成 user 消息写进去，模型会以为这些话是用户说的，有时会顺着去"回应"摘要本身。

这里还有个容易忽略的细节： 摘要要另起一条 System，别拼进原来那条。 因为 Prompt Caching 是按前缀匹配的，静态人设每轮都一样、能稳定命中缓存，而摘要每次压缩都会变。拼成一条，摘要一变整个 System 的缓存就会失效；拆成两条，前面那条静态的仍然能稳定命中缓存。

要提醒的是，这个写法是 OpenAI 风格的。Anthropic 的 system 是顶层参数、不在 messages 数组里，也只能是一个字符串，没法追加第二条，因此，摘要只能拼进 system 字符串（牺牲缓存），或者当成带显式标记的 user 消息发。

这里只是针对对话这个场景，给你展示了如何进行历史消息过长的处理，后面，我们在讲到Agent开发的时候，还会有专门的一个专题：上下文工程，来讲如何在有限的上下文窗口内，放置最有价值的信息。

五、多用户与长期历史存储

前面 history 用的是全局变量，只是为了演示而简化代码。真实应用有成千上万用户同时在聊，你必须解决两个问题。

第一，会话隔离。 每个用户、甚至同一用户的每个会话，都要有独立的历史，绝不能互相混用。踩过的坑是把历史存成全局或单例，结果 A 用户看到了 B 用户的对话。这是严重的隐私事故。正确做法是用 session_id （或 user_id + conversation_id ）作为 key，分别存储。

第二，历史存哪。 只存在内存里并不可靠，服务一重启历史会全部丢失，多实例部署时请求还可能被负载均衡路由到不同实例。因此，生产方案通常是：

  • 热数据放缓存（如 Redis），读写快，适合正在进行的会话，可设过期时间自动清理；
  • 全量/长期历史落数据库（如 MySQL、MongoDB），持久、可追溯、支持跨设备续聊。

存储的可以是完整历史，每次真正发给模型的，是经过裁剪/摘要后的版本。 你库里存全量便于审计和回溯，发给模型的则是精挑细选、控制在预算内的那一份。两者分离，才能兼顾成本与可靠。

同样，这里也只是简单讲了对话这个场景如何记录历史消息，在后面讲到的 Agent 的时候，我们还会详细讲解 Agent 的状态管理和记忆系统，会复杂得多。
