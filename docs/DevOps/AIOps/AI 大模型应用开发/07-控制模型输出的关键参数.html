07-控制模型输出的关键参数

上一篇我们把 messages 数组讲清楚了，知道了怎么组织消息、怎么实现多轮对话。但真正用起来，你很快会碰到一个难以预期的现象。

同样一段代码、同样一句提问，今天模型答得规规矩矩，明天突然就发散了，格式也偏离了预期。甚至同一次运行连着调两遍，结果都能不一样。

这不是 bug，是feature。模块一讲原理的时候说过：模型每生成一个 Token，都是在一批候选词上按概率抽样，而抽样这个动作本身就带随机性。

那既然随机性来自抽样，能不能在调用的时候调几个参数，让它该稳定时稳定、该多样时多样？

能。这些参数叫 采样参数（Sampling Parameters） ，是你作为开发者控制模型输出最直接的手段。这一篇我们就把它们一个个讲清楚。

一、模型是怎么「选下一个词」的

要讲清楚这些参数到底在调什么，得先回到生成的那一瞬间。

模型每生成一个 Token，会先给词表里每个候选词算一个分数，再用一个叫 Softmax 的函数把它们归一化成一组概率。比如你输入「今天天气」，模型算出来可能是这样：

很    40%
不    25%
真    15%
挺     8%
...   剩下的分散在长长的尾巴上

到这一步为止，一切都是确定的。同样的输入、同样的模型，算出来的概率分布一模一样。

真正的分歧发生在下一步： 拿到这组概率，到底选哪个？

一种做法是永远选概率最高的那个，也就是「很」。这叫 贪心解码（Greedy） 。好处是稳定，同样的输入永远给出同样的输出；坏处是呆板，而且特别容易陷入重复，写着写着开始反复重复同一句话。

另一种做法是按概率随机抽一个。你可以把这组概率想象成一个 抽奖转盘 ：「很」占了转盘 40% 的面积，「不」占 25%，「真」占 15%，剩下几千个词挤在最后那一点点扇形里。模型转一下指针，落到谁头上就选谁。这样输出灵活、有变化，但偶尔会抽到一个奇怪的词，然后顺着那个词一路偏离上下文。

主流模型默认走的是第二条路。所以开头说的「同一个问题问两次，答案不一样」，根源就在此。

采样参数要解决的，就是在这两个极端之间找平衡。说到底它们只干两件事：

一是微调这组候选的概率值，二是决定哪些候选有资格参加抽样。

具体怎么做，我们接着往下看！

二、温度 Temperature

温度是最常用的一个参数。它干的事情，用一句话说就是 给概率分布整形 ：把它拉得更尖，或者摊得更平。

温度调低，高概率的词会被进一步拉高，低概率的词被压得更低，整个分布变得又陡又尖。模型几乎每次都选中那个最可能的词，输出稳定、保守。温度调高则相反，词与词之间的差距被抹平，原本概率很低的词被选中的机会也变大了，输出更多样，当然也更容易偏离预期。

这里有个关键点必须先说清楚，很多人会搞错： 不管温度调到多少，Token 的概率排序永远不变。 冠军还是冠军，亚军还是亚军。温度改变的是「冠军的领先优势有多大」，而不是「冠军是谁」。

回到转盘的比喻：温度不换转盘上的选手，只调整每个人占多大的扇形。

拿前面那组概率举例，不同温度整形之后大致是这样（数字仅为示意）：

T = 0      很 100%                        强制选冠军，等价于贪心解码
T = 0.2    很 85%   不 10%   真  3%        极度拉尖，几乎只出冠军
T = 0.7    很 60%   不 25%   真 10%        适度拉尖，偶尔冒出亚军
T = 1.0    很 40%   不 25%   真 15%        原始分布，不做任何整形
T = 1.3    很 33%   不 26%   真 20%        明显抹平，亚军季军机会大增
T = 1.8    很 28%   不 24%   真 21%        接近平均分配，输出连贯性明显下降

在这张表里， 温度 1.0 是基准线，意思是不做任何整形，原始概率原样拿来抽奖。 低于 1 是拉尖，高于 1 是抹平。不少人以为 1.0 已经很高了，其实它只是「什么都没做」，也正因为如此，它是大多数厂商的默认值，很适合当调参的起点。

再看最后一行。温度到了 1.8，前三名的概率几乎持平，近似均匀抽取。这时候模型说出来的话往往语法还通顺，但逻辑急剧下降，偏离主题、前后矛盾都很常见。

# 低温：连着跑几次，措辞高度相似
curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-5.6",
    "messages": [{"role": "user", "content": "用一句话形容大海"}],
    "temperature": 0.2
  }'

# 高温：连着跑几次，每次都不太一样
curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-5.6",
    "messages": [{"role": "user", "content": "用一句话形容大海"}],
    "temperature": 1.3
  }'

这里得提醒一下： 温度这个数字，在不同厂商那里不是一回事。

首先是取值范围。OpenAI 和 DeepSeek 都是 0 ~ 2、默认 1，但也有厂商只开放 0 ~ 1。同样填 0.8 ，在前者那里只是偏高一点点，在后者那里已经接近上限了。顺带一提，虽然上限给到 2，OpenAI 的建议是 在 0 ~ 1 之间调最有效 ，越过 1 之后输出质量下滑得很快，这和上面那张表的观察是一致的。

三、核采样 Top P

温度解决了「分布多陡」的问题，但 它只负责整形，不负责筛选。

什么意思呢？哪怕你把温度压到 0.3，那些概率本来就只有 0.1% 的垃圾候选，比如乱码字符、莫名其妙的标点、毫不相关的生僻字，依然待在转盘上，只是占的扇形更小了而已。

但「更小」不等于「没有」。只要它还占着一小块面积，理论上就有被抽中的可能。万一某次运气不好，指针恰好落在上面，模型就会生成一个莫名其妙的符号，然后顺着这个错误一路写下去，整段回答会明显偏离，后续内容也跟着错下去。这种偶发的异常输出，在生产环境里不可接受。

所以我们需要另一个参数，来干一件温度干不了的事： 把那些概率极低的候选直接从转盘上去掉，让它们连参与抽奖的资格都没有。 这就是 Top P，学名核采样（Nucleus Sampling）。

它的做法是： 先把候选词按概率从高到低排好队，从头开始累加，累计概率一旦达到 P 就停止，只让选中的这批词参与抽样，后面长长的尾巴全部扔掉。

还是刚才那组概率，把后面的尾巴也列出来，假设 Top P 设成 0.9：

很    40%    累计 40%    ✓ 入选
不    25%    累计 65%    ✓ 入选
真    15%    累计 80%    ✓ 入选
挺     8%    累计 88%    ✓ 入选
凉     5%    累计 93%    ✓ 入选  ← 累计首次越过 90%，到此为止
──────────────────────────────────────
。     3%                ✗ 出局
啊     2%                ✗ 出局
呢     1%                ✗ 出局
后面几千个词（含各种乱码）   ✗ 出局

候选池只剩前五个，那些 3%、2%、1% 的偏门 Token 连上转盘的资格都没有了。这样既保留了灵活性，又把明显不合理的词排除在外。

反过来， Top P = 1.0 等于完全不设限，所有 Token 都能参与抽奖 ，而这恰恰是大多数 API 的默认值。实践中一般建议设到 0.9 到 0.95 之间，既能滤掉乱码，又不至于把候选池压得太死、让模型可选词过少，输出过于单一。

两者的区别，一句话总结一下： 温度改的是「每个候选被选中的相对概率」，Top P 改的是「哪些候选有资格参与抽样」。

curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-5.6",
    "messages": [
      {"role": "system", "content": "你是一个资深的 Python 工程师。"},
      {"role": "user", "content": "帮我写一个快速排序算法"}
    ],
    "temperature": 0.2,
    "top_p": 0.9,
    "max_tokens": 1000
  }'

四、最大输出长度 max tokens

max_tokens （有些厂商叫 max_output_tokens ）限制的是模型这一次 最多能生成多少 Token 。

要特别注意它的语义：它不是告诉模型「你写这么长」，而是「写到这里就强制掐断」。模型自己并不知道有这个限制，它只是写着写着，突然被中途截断。

它有两个用途。一是控制成本，输出 Token 通常比输入贵好几倍；二是防止模型输出过长、没有止境。

那怎么知道是不是被截断了？看响应里的 finish_reason 字段：

  • stop ：模型自然说完了，正常结束。
  • length ：超过了长度上限被截断，内容不完整。

我们故意把 max_tokens 设小，看看会发生什么：

curl https://api.openai.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -d '{
    "model": "gpt-5.6",
    "messages": [{"role": "user", "content": "详细解释一下什么是数据库事务"}],
    "max_tokens": 30
  }'

返回是这样的（省略了无关字段）：

{
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "数据库事务（Transaction）是指作为一个整体来执行的一组数据库操作，这组操作要么全部成功"
      },
      "finish_reason": "length"
    }
  ],
  "usage": { "prompt_tokens": 18, "completion_tokens": 30, "total_tokens": 48 }
}

注意两点： content 在「要么全部成功」这里戛然而止，后半句没了；而 finish_reason 是 length ，这就是它在告诉你「我没说完，是被掐断的」。

说个真实会踩的坑： 让模型输出 JSON。 max_tokens 设小了，模型写到 {"name": "张三", "age": 就被切断，你的代码一解析就直接抛异常。

所以 凡是消费模型输出的地方，先检查 finish_reason ，是 length 就报警或者重试，别默认它一定完整。

还有一个容易忽略的点。用推理模型的时候，思考过程也算 Token，和最终答案共享同一份 max_tokens 配额。所以开了思考模式，这个值要比平时留得宽裕得多，否则很容易出现「思考过程已经消耗了大量 Token，答案还没开始写就没配额了」的尴尬情况。
