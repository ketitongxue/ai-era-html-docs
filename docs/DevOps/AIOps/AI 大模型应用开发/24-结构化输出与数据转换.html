24-结构化输出与数据转换

模块二第 4 篇专门讲过结构化输出，当时的结论是：想拿到可靠的 JSON，需要三个步骤，用 Schema 约束模型、用程序校验结果、校验失败带着错误信息重试。那一篇的代码全是手写的：手写 JSON Schema、手写反序列化和校验、手写重试循环。

这一篇来看框架是怎么封装这三个步骤的。

一、几行代码完成结构化输出

先看两边最简单的写法。

Spring AI ：定义一个 record ``ExpenseClaim ，然后把结尾的 .content() 换成.entity() ，于是就直接得到了 ExpenseClaim`对象。

record ExpenseClaim(String employee, String city, int amount, String category) {}

ExpenseClaim claim = chatClient.prompt()
        .user("从这段报销申请里抽取结构化信息：" + rawText)
        .call()
        .entity(ExpenseClaim.class);   // 不再是 .content()

LangChain ：定义一个 Pydantic 模型，然后用 with_structured_output 指定输出类型。

from pydantic import BaseModel, Field

class ExpenseClaim(BaseModel):
    """一条报销申请的结构化信息。"""
    employee: str = Field(description="报销人姓名")
    city: str = Field(description="出差城市")
    amount: int = Field(description="报销金额，单位元，取整数")
    category: str = Field(description="费用类别：住宿/交通/餐饮/其他")

structured_model = model.with_structured_output(ExpenseClaim)
claim = structured_model.invoke(f"从这段报销申请里抽取结构化信息：{raw_text}")

两边都只需几行代码，它们底层做的事情是：

  1. 从你的类型生成 JSON Schema。 Java record 的字段、Pydantic 模型的注解，被反射成一份 JSON Schema。
  2. 把这份 Schema 交给模型。 具体怎么交，有两条不同的路径，第三节会展开讲。
  3. 把模型返回的 JSON 反序列化成对象。 Spring AI 用 Jackson，LangChain 用 Pydantic。

这三件事就是模块二里手写的那三个步骤。框架没有发明新的机制，它只是把这套流程帮我们实现了。

另外需要说明： 结构化输出和流式是互斥的。 Spring AI 的 .entity() 明确只支持 call() ，因为要拿到完整响应才能解析。LangChain 也一样。

二、从类型自动生成 JSON Schema

模块二里，JSON Schema 是我们自己写的一份 JSON。用上框架之后，这份 Schema 不再手写，而是从类型定义里自动生成。你写的是一个普通的 Java record 或 Pydantic 模型，框架用反射把字段名、类型、必填项和描述抽出来，拼成第三节要交给模型的那份 Schema。

这样做之后，你只需要维护一份类型定义。以前手写 Schema 时，JSON Schema、类型定义、解析代码是三份东西，一处改了、另一处没跟着改的情况很常见。现在这份类型定义同时承担三件事： 发给模型当格式说明、反序列化时当校验规则，也是代码里最终拿到的业务对象。

写类型的时候，最容易漏掉的是字段上的描述。很多人只写字段名和类型，把描述当成给同事看的注释。其实不是。框架会把这些描述原样写进 Schema，再随 Schema 一起发给模型。模型判断 amount 该填 800 还是 800.00、单位是「元」还是「分」，靠的就是这段文字。字段名写成 amt 、描述又留空，模型就只能猜测。

拿第一节的 ExpenseClaim 来说，它转化成了Schema如下所示：

{
  "description": "一条报销申请的结构化信息。",
  "properties": {
    "employee": {
      "description": "报销人姓名",
      "title": "Employee",
      "type": "string"
    },
    "city": {
      "description": "出差城市",
      "title": "City",
      "type": "string"
    },
    "amount": {
      "description": "报销金额，单位元，取整数",
      "title": "Amount",
      "type": "integer"
    },
    "category": {
      "description": "费用类别：住宿/交通/餐饮/其他",
      "title": "Category",
      "type": "string"
    }
  },
  "required": ["employee", "city", "amount", "category"],
  "title": "ExpenseClaim",
  "type": "object"
}
  • 类名变成顶层的 title ，类的 docstring 变成顶层的 description 。
  • 每个字段变成 properties 下的一项，Python 的类型注解变成 type （ str 对应 string ， int 对应 integer ）。
  • Field(description=...) 原样变成该字段的 description 。
  • 没有给默认值的字段，全部被收进 required 。

Spring AI 中字段描述的写法是 Jackson 的 @JsonPropertyDescription ：

record ExpenseClaim(
        @JsonPropertyDescription("报销人姓名，取申请单上的签字人") String employee,
        @JsonPropertyDescription("出差城市，只写城市名，不带省份") String city,
        @JsonPropertyDescription("报销金额，单位元，取整数") int amount,
        @JsonPropertyDescription("费用类别，只能是：住宿、交通、餐饮、其他") String category) {}

这里有一个细节，值得注意：字段的顺序也讲究。模型生成 JSON 时是从前往后逐个字段生成，先生成的值会成为后面字段的上下文。

Spring AI 支持用 @JsonPropertyOrder 指定这个顺序。 把需要先确定的字段排在前面，后面的字段就更容易写对。 比如先输出 category 再输出 amount ，模型在填金额时已经知道这是住宿还是交通；反过来先填金额，类别反而可能对不上。

Pydantic 这边没有这个注解，字段顺序就是你在类里声明的顺序，把该先确定的字段写在前面即可。

三、JSON Schema的约束方式

模块二讲过，让模型产出 JSON 格式的结构化输出，有三层强度依次递增的约束方式：只把格式要求写进提示词、用 json_object 保证输出是合法 JSON、用 json_schema 按 Schema 强约束。

下面按从弱到强的顺序，分别看两个框架怎么实现这三层。

第一层：只把 Schema 拼进提示词

这一层最简单：把生成的 JSON Schema 转成一段格式说明，追加到提示词末尾。

Spring AI 的默认行为就是这一层，即第一节写的 .entity() 不加任何参数：

ExpenseClaim claim = chatClient.prompt()
        .user("从这段报销申请里抽取结构化信息：" + rawText)
        .call()
        .entity(ExpenseClaim.class);   // 默认行为：Schema 拼进提示词

LangChain 要实现这一层约束，格式说明需要你自己拼进提示词：

from langchain_core.output_parsers import PydanticOutputParser
from langchain_core.prompts import ChatPromptTemplate

parser = PydanticOutputParser(pydantic_object=ExpenseClaim)

prompt = ChatPromptTemplate.from_template(
    "从这段报销申请里抽取结构化信息：{text}\n\n{format_instructions}"
).partial(format_instructions=parser.get_format_instructions())

claim = (prompt | model | parser).invoke({"text": raw_text})

第二层：json_object，只保证语法合法

有一点必须清楚： 这一层不能替代第一层，只能叠加在它上面。 有哪些字段、每个字段什么含义、什么类型，仍然只能靠提示词里的 Schema 来说明。

LangChain 对应 method="json_mode" ：

structured_model = model.with_structured_output(ExpenseClaim, method="json_mode")

但只写这一行不够。 这里传进去的 ExpenseClaim 不会发给模型，它只用来解析返回值，实际发出去的 response_format 里只有一个 {"type": "json_object"} 。字段说明仍然要自己拼进提示词：

from langchain_core.output_parsers import PydanticOutputParser
from langchain_core.prompts import ChatPromptTemplate

structured_model = model.with_structured_output(ExpenseClaim, method="json_mode")

instructions = PydanticOutputParser(
    pydantic_object=ExpenseClaim).get_format_instructions()

prompt = ChatPromptTemplate.from_template(
    "从这段报销申请里抽取结构化信息：{text}\n\n{format_instructions}"
).partial(format_instructions=instructions)

claim = (prompt | structured_model).invoke({"text": raw_text})

Spring AI 没有为这一层提供跨厂商的统一开关，需要用厂商特有的选项类：

ExpenseClaim claim = chatClient.prompt()
        .user("从这段报销申请里抽取结构化信息，用 JSON 返回：" + rawText)
        .options(OpenAiChatOptions.builder()
                .responseFormat(ResponseFormat.builder().type(ResponseFormat.Type.JSON_OBJECT).build())
                .build())
        .call()
        .entity(ExpenseClaim.class);

客观地说，这一层的实用价值在下降，因为支持 json_schema 的模型越来越多。 它的定位是过渡方案 ：模型支持 json_object 但还不支持 json_schema 的时候用它，比纯提示词多一层保障。

第三层：json_schema，把 Schema 变成 API 合同

这一层是把 Schema 作为一个独立的 API 字段发过去，由厂商的运行时保证返回结果符合要求，提示词里不再需要追加格式说明（既节省 Token，提示词也更简洁）。

Spring AI 的启用方式：

ExpenseClaim claim = chatClient.prompt()
        .user("从这段报销申请里抽取结构化信息：" + rawText)
        .call()
        .entity(ExpenseClaim.class, spec -> spec.useProviderStructuredOutput());

Spring AI 是通过检查模型的选项类有没有实现 StructuredOutputChatOptions ，来判断厂商是否支持 json_schema 。 如果不支持，这个开关会被静默忽略，自动退回第一层的提示词方案。

LangChain 对应 method="json_schema" ：

structured_model = model.with_structured_output(ExpenseClaim, method="json_schema")

四、校验与待反馈重试

模块二讲到：解析失败之后， 不要直接重发同一条请求，要把具体的错误信息带回去 ，让模型知道自己错在哪里。Spring AI 把这个功能做成了内置能力，LangChain 需要你自己实现。

Spring AI：使用 validateSchema() 。

ExpenseClaim claim = chatClient.prompt()
        .user("从这段报销申请里抽取结构化信息：" + rawText)
        .call()
        .entity(ExpenseClaim.class, spec -> spec.validateSchema());

它背后是自动注册的 StructuredOutputValidationAdvisor ，流程是这样的：

想修改重试次数，需要自己创建一个 Advisor 注册上去，显式注册的会替换掉自动注册的那个：

var validationAdvisor = StructuredOutputValidationAdvisor.builder()
        .outputType(ExpenseClaim.class)
        .maxRepeatAttempts(5)
        .build();

ChatClient chatClient = builder.defaultAdvisors(validationAdvisor).build();

LangChain 没有提供 Spring AI 那种开箱即用的自动重试，需要你拿到失败信息之后自己决定怎么处理：

structured_model = model.with_structured_output(ExpenseClaim, include_raw=True)
result = structured_model.invoke(prompt)

result["raw"]            # 原始 AIMessage，Token 用量在这里面
result["parsed"]         # 解析成功时的对象，失败时是 None
result["parsing_error"]  # 解析失败时的异常

注意默认行为：不加 include_raw ，解析失败会直接抛异常。 加上之后异常转换为 parsing_error 。
